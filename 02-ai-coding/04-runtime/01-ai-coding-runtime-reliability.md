# AI Coding 运行可靠性：AI 看不到的生产环境

> AI Coding 带来的最大工程风险，从来不是“代码写不出来”或“语法不对”，而是代码在本地测试全绿、Review 看着优雅，一上生产就雪崩。根本原因是信息不对称：AI 看到的只是静态的代码库和少量 Mock 测试，而生产环境是一个充满状态、并发、脏数据和隐式依赖的动态系统。
>
> **适用范围与时效说明：** 本文对应 [AI Coding 常见问题与治理要点](../01-problems/01-ai-coding-common-problems.md) 中的 33 生产环境行为偏差、34 数据演进问题、35 并发与分布式问题和 36 故障恢复机制缺失。文中的机制属于工程实践建议，第 5 节是示意案例，第 7 节的实验尚未实测。各工具的能力和配置方式以其当前文档为准。本文核对时间：2026 年 11 月。

## 1. TL;DR

| 问题 | 结论 |
| --- | --- |
| 核心问题 | 信息不对称：AI 只看到静态代码和 Mock 数据，看不到生产的数据规模、并发时序、隐式契约、基础设施约束和业务不变量 |
| 核心思路 | 不指望模型变得“全知”，而是建一套工程体系：能暴露的生产约束安全地左移给 AI；不能暴露的，用确定性护栏拦在发布前；防不住的，用爆炸半径控制关在笼子里 |
| 四层架构 | 生产上下文左移 → 确定性验证与仿真 → 运行时防御与渐进发布 → 生产反馈闭环 |
| 关键机制 | 生产画像、只读脱敏的观测接入、约束代码化、SQL 执行计划门禁、流量回放、契约与属性测试、硬超时与数据库约束、金丝雀发布与自动回滚、事故转规则 |
| 主要成本 | 影子环境和流量回放的建设成本、门禁误报、渐进发布拉长上线时间 |
| 不要做 | 把生产数据库或含个人信息的原始日志直接交给模型；指望 Code Review 发现生产隐患；AI 生成的变更一次性全量上线 |

## 2. 问题：AI 看不到的生产环境

### 2.1 信息不对称

AI 写代码时能看到的，是代码仓库、本地环境和测试数据。这些信息几乎都描述了“正常情况”：表里只有几十行数据，请求一个一个按顺序到达，依赖服务总是立刻返回，数据格式总是规范的。

生产环境正好相反。下表对比两边的差异：

| | AI 看到的 | 生产环境 |
| --- | --- | --- |
| 数据 | 几十条 Mock 数据，格式规范 | 数千万到数亿行，有热点和倾斜，夹杂历史遗留的脏数据 |
| 并发 | 请求依次到达 | 高并发、重复请求、消息重复投递和乱序 |
| 依赖 | 总是立刻返回 | 超时、限流、长尾延迟、部分失败 |
| 契约 | 接口文档上写的 | 文档没写、但下游已经依赖的行为 |
| 资源 | 本机资源充足 | 容器内存上限、连接池大小、第三方 QPS 限制 |
| 版本 | 只有当前版本 | 发布期间新旧版本同时运行 |

人写代码同样会犯这些错误，但有经验的开发者见过线上事故，会主动考虑这些情况。AI 没有这种经验；除非有人把这些信息给它，否则它写出的代码默认只适用于理想情况。

### 2.2 五类盲区

只有先看清盲区，方案才不会流于空谈。AI 在编码阶段主要缺失五类生产信息：

| 盲区 | 典型例子 | 对应问题 |
| --- | --- | --- |
| 数据规模与分布（Scale & Skew） | 表里是 100 行还是 5 亿行；有没有热点 Key、数据倾斜；有没有 null、非法格式、超长字段等历史脏数据 | 33、34 |
| 并发与时序（Concurrency & State） | 竞态条件、死锁、缓存击穿、分布式事务部分失败、重试风暴 | 35、36 |
| 隐式契约（Hyrum's Law） | 文档没写，但下游某个老系统依赖了返回字段的顺序、某个特定错误码，甚至某种空值表现 | 03、34 |
| 基础设施约束（Infra & Limits） | 容器内存上限、数据库连接池大小、上游第三方 API 的 QPS 限流、网络抖动和长尾延迟 | 33、36 |
| 业务不变量（Business Invariants） | “账户余额不能为负”“同一笔订单不能重复扣款”“核心链路不能强依赖非核心服务” | 04、35、36 |

隐式契约指的是 Hyrum 定律：当一个接口的使用者足够多时，接口所有可观察到的行为都会被某个使用者依赖，无论文档承诺了什么。AI 只能看到文档和代码，看不到这些依赖。

## 3. 应对思路：四层可靠性架构

核心思路不是让 AI 变得全知，而是分三种情况处理生产约束：

- **能暴露的，安全地左移给 AI**：把生产的关键特征结构化、脱敏后，放进 AI 的上下文。
- **不能暴露的，用确定性护栏拦在发布前**：用自动化的门禁和仿真代替人工判断。
- **防不住的，用爆炸半径控制关在笼子里**：默认 AI 代码一定会出错，在架构上限制它出错时的影响。

最后，再把每一次线上问题转化为永久的约束，反馈给前面三层。

```text
[生产现实] ──（1. 脱敏、抽象后左移）──▶ [AI 编码阶段]
                                            │ 生成代码
                                            ▼
                                  [2. 确定性验证与仿真]   ── 在发布前拦截隐患
                                            │ 准入发布
                                            ▼
                                  [3. 运行时防御与渐进发布] ── 控制爆炸半径
                                            │ 线上运行
                                            ▼
                                  [4. 生产观测 → 规则闭环]  ── 反哺 AI 上下文和护栏
```

| 层 | 解决的问题 | 依靠什么 |
| --- | --- | --- |
| 第一层：生产上下文左移 | AI 不知道生产是什么样 | 生产画像、只读观测接入、约束代码化 |
| 第二层：确定性验证与仿真 | AI 知道了也可能写错，人工审查跟不上 | 执行计划门禁、流量回放、对抗性测试 |
| 第三层：运行时防御与渐进发布 | 前两层总有漏网之鱼 | 硬超时、数据库约束、隔离与熔断、金丝雀发布 |
| 第四层：生产反馈闭环 | 同样的错误反复出现 | 事故转规则、基于观测的诊断 |

第一层属于问题清单第 3 节所说的“说明文件中的指令”和“可复用的工具与组件”，只能降低出错的概率；第二、三层是强制手段。33–36 都是高风险问题，不能只靠第一层。

## 4. 四层机制

### 4.1 第一层：生产上下文左移

不要把生产环境当作黑盒，而是把生产的关键特征结构化、脱敏化、机器可读化，接入 AI 的上下文。原则是：**让 AI 看见，但绝不越界。**

**机制一：生产画像（Metadata-as-Context）。**

在代码仓库中维护一份由 CI 定时自动生成的“生产画像”，只包含元数据和统计信息，不包含任何业务数据。示例（数据为示意）：

```yaml
# docs/prod-profile.yaml
# 由 CI 每周从生产元数据自动生成，只包含统计信息，不包含任何业务数据。请勿手工修改。
generated_at: "2026-11-20"

tables:
  users:
    rows: 30000000          # 约 3000 万行
    daily_growth: 50000
    indexes:
      - "pk (id)"
      - "idx_users_email (email)"
      - "idx_users_created_at (created_at)"
    notes:
      - "status 字段只有 3 个取值，单独按它过滤会扫描大量数据"
      - "ext_json 字段存在早期迁移留下的非法 JSON，必须使用容错反序列化"
      - "严禁在主库上做大范围扫描；报表类查询走只读从库，并使用游标分页"
  orders:
    rows: 200000000         # 约 2 亿行
    hot_keys: "大促期间少数商家的订单量占比极高"

services:
  order-api:
    sla: { p99_ms: 50, peak_qps: 5000 }

dependencies:
  payment-gateway:
    timeout_ms: 800
    rate_limit_qps: 200     # 第三方限流红线
```

行数、索引等信息可以从数据库的系统表获取（例如 PostgreSQL 的 `pg_class.reltuples`、`pg_indexes`），SLA 和 QPS 可以从监控系统获取。AI 看到 `orders` 有 2 亿行，就不会写出无索引的 `LIKE` 查询或全表扫描。

**机制二：只读的生产观测接入。**

通过只读、严格鉴权的 MCP Server 或工具接口，让 AI 在改代码和排查问题时，查询脱敏后的生产遥测数据：

- OpenTelemetry 链路追踪：真实调用链路的上下游依赖和耗时分布。
- 慢查询日志和 `EXPLAIN` 执行计划。
- 线上错误聚合（如 Sentry、Datadog）：高频报错的指纹，以及脱敏后的异常载荷结构。

安全红线：

- 严禁把生产数据库或含个人信息的原始日志直接交给模型。只暴露表结构、统计分布和脱敏后的异常样本。
- 观测接口按 [AI Coding 安全与合规](../03-security/01-ai-coding-security.md) 4.5 节的做法，只授予只读权限。
- 日志和异常载荷来自外部输入，可能夹带注入指令，按安全与合规 4.4 节的规则，只作为数据处理。

**机制三：隐式知识代码化（Constraints & Invariants as Code）。**

把老员工脑子里的“生产禁忌”写成 AI 必须遵守的规范，放进仓库级的说明文件（如 `AGENTS.md`）：

```markdown
## 生产禁忌

- 禁止在数据库事务内发起外部 HTTP 调用。
- 禁止无分页的 findAll 或全量查询；列表查询必须带分页，单页上限 500 条。
- 写操作和消息消费必须带幂等 Key，使用 `IdempotentConsumer` 基类或请求去重组件。
- 新增外部调用必须使用统一的 HTTP 客户端封装，并设置超时，不得使用默认的无限超时。
- 修改接口时，不得改变已有字段的含义、类型、顺序和空值表现；需要变化时，新增字段或新增版本。
- 跨系统写操作在实现前，先写出失败矩阵（见下文）。
```

下游契约用 OpenAPI、Protobuf 或 JSON Schema 定义成强契约，禁止随意更改字段语义。

跨系统写操作的**失败矩阵**，要求 AI 在实现前写出来，并经人工评审确认：

| 步骤 | 失败时系统处于什么状态 | 处理方式 |
| --- | --- | --- |
| 1. 创建订单 | 无副作用 | 直接返回失败 |
| 2. 扣减库存 | 订单已创建，库存未扣 | 订单标记为失败 |
| 3. 调用支付 | 库存已扣，支付结果未知 | 查询支付状态；超时未知时进入待对账，不直接重试扣款 |
| 4. 更新订单为已支付 | 支付成功，订单状态未更新 | 由支付回调或定时对账补偿 |

这一层只能降低出错的概率。规范写得再好，AI 也可能漏看，所以需要第二层。

### 4.2 第二层：确定性验证与仿真

AI 产出代码的速度远高于人工审查的速度（问题 28），靠人工 Code Review 发现生产隐患必然会失效。必须把“人工判断生产隐患”升级为“自动化的确定性门禁”，用确定的规则卡住模型的概率性输出。

**机制一：SQL 执行计划门禁。**

在 CI 中维护一个影子库：表结构和索引与生产一致，数据量级和分布接近生产。不需要拷贝真实数据，可以使用脱敏抽样数据，或按生产统计信息生成合成数据。

对 AI 新增或修改的 SQL 自动运行 `EXPLAIN`，出现大表全表扫描、预估扫描行数超过阈值时，阻止合并：

```python
#!/usr/bin/env python3
"""对 SQL 运行 EXPLAIN，发现大表全表扫描和预估行数过多的查询。

用法：SHADOW_DB_DSN=postgresql://... python explain_gate.py queries.sql
  queries.sql 中每条 SQL 以分号结尾，可以包含 $1、$2 这样的参数占位符。
依赖：psycopg 3（pip install "psycopg[binary]"）。
参数化查询依赖 EXPLAIN 的 GENERIC_PLAN 选项，需要 PostgreSQL 16 及以上。
只运行 EXPLAIN，不运行 EXPLAIN ANALYZE，查询本身不会被执行。
"""
import json
import os
import sys

import psycopg

SEQ_SCAN_MAX_TABLE_ROWS = 100_000   # 超过这个行数的表，不允许全表扫描
MAX_NODE_ROWS = 1_000_000           # 任一计划节点的预估行数上限（含排序、连接）


def walk(node):
    yield node
    for child in node.get("Plans", []):
        yield from walk(child)


def table_rows(conn, schema, table):
    row = conn.execute(
        "SELECT c.reltuples FROM pg_class c "
        "JOIN pg_namespace n ON n.oid = c.relnamespace "
        "WHERE n.nspname = %s AND c.relname = %s",
        (schema, table),
    ).fetchone()
    return row[0] if row else 0


def check_plan(plan, rows_of):
    problems = []
    for node in walk(plan):
        node_type = node.get("Node Type")
        if node_type == "Seq Scan":
            table = f'{node.get("Schema", "public")}.{node.get("Relation Name")}'
            total = rows_of(node.get("Schema", "public"), node.get("Relation Name"))
            if total > SEQ_SCAN_MAX_TABLE_ROWS:
                problems.append(f"全表扫描 {table}（约 {int(total)} 行）")
        if node.get("Plan Rows", 0) > MAX_NODE_ROWS:
            problems.append(f"{node_type} 预估 {node['Plan Rows']} 行，超过上限 {MAX_NODE_ROWS}")
    return problems


def main():
    sql_text = open(sys.argv[1], encoding="utf-8").read()
    queries = [q.strip() for q in sql_text.split(";") if q.strip()]
    failed = False
    with psycopg.connect(os.environ["SHADOW_DB_DSN"]) as conn:
        for query in queries:
            options = "FORMAT JSON, VERBOSE" + (", GENERIC_PLAN" if "$" in query else "")
            result = conn.execute(f"EXPLAIN ({options}) {query}").fetchone()[0]
            plan = (json.loads(result) if isinstance(result, str) else result)[0]["Plan"]
            problems = check_plan(plan, lambda s, t: table_rows(conn, s, t))
            if problems:
                failed = True
                print(f"[阻止] {query[:80]}")
                for p in problems:
                    print(f"    - {p}")
    sys.exit(1 if failed else 0)


if __name__ == "__main__":
    main()
```

ORM 生成的 SQL 不直接写在代码里，可以在 CI 运行测试时打开 ORM 的 SQL 日志，收集实际执行的语句，再交给这个脚本。按分号切分 SQL 的方式很粗糙，字符串里含分号的语句需要单独处理。阈值按项目调整。

**机制二：生产流量录制与影子回放（Shadow Traffic Replay）。**

这是解决“AI 没见过真实脏数据和隐式契约”最有效的手段。通过网关或 Sidecar（如 Envoy 的 tap 功能、GoReplay），把生产的真实**读**流量异步镜像到部署了新代码的影子环境，再用 Diffy 这类工具对比新旧版本：

- **响应对比**：发现破坏隐式契约、边界空值处理不一致的问题。
- **资源对比**：在真实流量形态下，暴露内存泄漏、CPU 暴涨、连接池耗尽。

只回放读流量。写流量回放会产生真实的副作用，需要专门的隔离方案。回放环境要和生产一样做好数据保护，不能让镜像流量中的个人信息流出。

**机制三：用对抗性验证代替浅层单测。**

AI 为自己的代码写的单元测试往往有“自证偏见”：自己写的 Bug，测试也会绕开（见 [AI Coding 验证体系](../02-verification/01-ai-coding-verification.md) 第 2 节）。在 CI 中强制引入：

- **契约测试**（如 Pact）：确认没有破坏下游依赖的行为，包括文档没写但下游实际依赖的部分。
- **属性测试和模糊测试**（如 Python 的 Hypothesis、Java 的 jqwik、JavaScript 的 fast-check）：自动生成超长字符串、畸形 JSON、空值、极值数字，专门检验代码对生产脏数据的处理。
- **并发检测和幂等测试**：如 Go 的 `go test -race` 检测数据竞争；模拟高并发和重复投递，检验同一请求执行多次的结果是否一致。用 ArchUnit 等架构测试检查消息消费者是否继承了幂等基类。

### 4.3 第三层：运行时防御与爆炸半径控制

无论发布前的检查多严密，总会有漏网之鱼。架构上要采取零信任假设：**默认 AI 生成的代码一定会出错**，把它当作不可信组件来隔离。

**机制一：硬性运行时护栏。**

护栏放在框架、驱动和数据库层面，而不是依赖每段业务代码自己写对：

- **全链路硬超时和上限**：在数据库账号或驱动层设置默认语句超时和最大返回行数。即使 AI 忘了写 `LIMIT`，也会被框架拦下，而不是拖垮数据库。

  ```sql
  -- 报表账号的语句超时 2 秒，连接到只读从库
  ALTER ROLE report_reader SET statement_timeout = '2s';
  ```

- **资源隔离和熔断**：新功能和非核心链路使用独立的线程池和连接池（舱壁模式），配置熔断和降级，防止局部的死循环或慢查询引发级联雪崩。
- **运行时不变量断言**：在资金、库存、权限等核心状态变更点，由数据库约束或框架执行硬校验，而不是依赖业务逻辑：

  ```sql
  -- 余额不能为负
  ALTER TABLE accounts ADD CONSTRAINT chk_balance_non_negative CHECK (balance >= 0);
  -- 同一笔订单只能有一条支付记录，从数据库层面防止重复扣款
  CREATE UNIQUE INDEX uq_payments_order_id ON payments (order_id);
  ```

**机制二：数据库变更的渐进发布。**

发布期间新旧版本同时运行，数据库变更必须同时兼容两个版本。采用“先扩展、再迁移、后收缩”（Expand / Migrate / Contract），以把 `users.phone` 改名为 `users.mobile` 为例：

| 阶段 | 数据库变更 | 应用发布 |
| --- | --- | --- |
| 1. 扩展 | 新增 `mobile` 列，允许为空 | 新版本同时写 `phone` 和 `mobile`，读 `phone` |
| 2. 迁移 | 分批把历史数据从 `phone` 回填到 `mobile` | 回填完成并校验一致后，改为读 `mobile` |
| 3. 收缩 | 确认没有任何版本再读写 `phone` 后，删除 `phone` 列 | 移除写 `phone` 的代码 |

每个阶段都可以单独回退。CI 检查迁移改动是否附带回滚脚本；大表变更先在影子库上演练，评估锁表时间，安排在业务低峰期执行，迁移上线前由 DBA 或模块负责人确认。

**机制三：渐进式发布和指标驱动的自动回滚。**

AI 生成的变更默认禁止一次性全量上线。结合功能开关（Feature Flag）和金丝雀发布：先放少量流量，基于黄金指标（错误率、P99 延迟、核心业务转化率、内存增长斜率）与基线自动对比，一旦异常自动回滚，不需要等人半夜起来看告警。

以 Argo Rollouts 为例（示意配置）：

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: export-api
spec:
  # selector、template 等其余字段省略
  strategy:
    canary:
      analysis:
        templates:
          - templateName: error-rate
        args:
          - name: service
            value: export-api
      steps:
        - setWeight: 5
        - pause: { duration: 10m }
        - setWeight: 25
        - pause: { duration: 10m }
        - setWeight: 50
        - pause: { duration: 10m }
---
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: error-rate
spec:
  args:
    - name: service
  metrics:
    - name: error-rate
      interval: 1m
      failureLimit: 2            # 连续失败 2 次即判定异常，触发回滚
      successCondition: result[0] < 0.01
      provider:
        prometheus:
          address: http://prometheus.monitoring:9090
          query: |
            sum(rate(http_requests_total{service="{{args.service}}",code=~"5.."}[2m]))
            /
            sum(rate(http_requests_total{service="{{args.service}}"}[2m]))
```

没有接入服务网格或流量网关时，流量比例只能通过副本数近似实现，副本较少时做不到 1% 这样的细粒度。

**机制四：影子写与双写校验。**

对核心重构、复杂计费和状态机逻辑，让新逻辑和老逻辑并行运行（Dark Launch）：新逻辑只计算、不落库，异步比对两者的结果，长时间完全一致后再切流。

### 4.4 第四层：生产反馈闭环

AI 不会因为一次事故就记住教训。必须把每次生产异常转化为永久的系统约束。

**机制一：事故转规则（Incident-to-Guardrail）。**

每当 AI 生成的代码在线上引发一次故障，复盘的终点不能是“修完 Bug 就结束”，必须至少产出以下三样之一：

1. 一条新的静态分析、Lint 或 CI 门禁规则，从机制上封死同类错误。
2. 一个脱敏后的生产回归测试用例，固化真实的脏数据或并发场景。
3. 一条精炼的仓库规范，更新到 `AGENTS.md`、生产画像或领域规则库。

在复盘模板中加入：

```markdown
## 护栏产出（必填，至少一项）

- [ ] 新增 CI / Lint 规则：<规则名称和链接>
- [ ] 新增回归测试用例：<用例路径，确认已脱敏>
- [ ] 更新仓库规范：<AGENTS.md 或生产画像的改动链接>

如果三项都不适用，说明原因：
```

三类产出的约束力不同：CI 规则是强制手段，测试用例和规范只能降低概率。能写成 CI 规则的，优先写成规则。

**机制二：基于生产观测的诊断闭环。**

线上指标异常时，把**本次发布的代码 diff、异常链路追踪、指标突变点**打包交给诊断 Agent，让 AI 第一次真正“看见”自己的代码在生产中造成的后果：定位根因，生成回滚建议或最小修复补丁。

诊断 Agent 只有只读权限，回滚和修复由人审批后执行，权限要求同安全与合规 4.5 节。

## 5. 一个示意案例：四层防线如何配合

下面是一个示意场景，用来说明四层机制如何配合，不是实际发生的事故。

**场景：** 用 AI 开发一个“导出活跃用户报表”的接口。AI 写出了很优雅的 ORM 代码，本地用 50 条 Mock 数据测试全部通过。但生产的 `users` 表有 3000 万行，`status` 字段基数低、没有联合索引，数据里还夹杂着早期迁移留下的非法 JSON 扩展字段。

**没有这套体系：** 上线后全表扫描拖垮主库，一次性加载数据导致 Pod 内存溢出，非法 JSON 让解析逻辑崩溃。

**有了四层防线：**

| 层 | 起到的作用 |
| --- | --- |
| 第一层 | AI 读到生产画像：`users` 表约 3000 万行，严禁在主库上大范围扫描，报表走只读从库并使用游标分页。生成代码时就避开了全表拉取 |
| 第二层 | 即使 AI 漏看了规范，CI 的执行计划门禁发现了大表全表扫描，阻止合并；属性测试和流量回放用畸形和脱敏的真实数据，提前暴露了非法 JSON 的解析异常 |
| 第三层 | 即使上线后遇到极端情况导致慢查询，只读从库和 2 秒语句超时保住了核心交易链路；金丝雀阶段该接口 5xx 升高，触发自动回滚 |
| 第四层 | 非法 JSON 的问题被固化为脱敏测试用例加入 CI，团队的 Lint 规则要求扩展字段必须使用容错反序列化封装 |

四层中任何一层单独起作用，都能减少损失；每一层都可能失效，所以需要多层叠加。

## 6. 团队落地路线图

不需要一次建成全套基础设施。按投入产出比，建议分三个阶段推进（周期为参考值）：

**第一阶段（约 1–2 周）：立规矩，设硬底线。** 投入低、见效快。

1. 在核心仓库建立机器可读的生产画像和生产禁忌（核心表量级、禁止模式、SLA 红线）。
2. 在框架和数据库层加上硬超时、默认分页上限、数据库约束（唯一索引、外键、CHECK），以及熔断和限流。
3. CI 增加针对 AI 高频出错点的静态门禁：SQL 审查、并发检测、禁止绕过框架的危险调用。

**第二阶段（约 1–2 个月）：消除盲区，控制发布。**

1. 建立表结构和数据分布与生产对齐的影子库，接入执行计划门禁和契约测试。
2. 核心服务落地功能开关、金丝雀发布和指标驱动的自动回滚。
3. 对高风险的核心接口，落地只读流量回放。

**第三阶段（长期演进）：形成闭环。**

1. 通过只读、脱敏的 MCP 接口，把链路追踪、慢查询和错误聚合安全地接入 AI 的编码和排障流程。
2. 建立“事故 → 回归用例和门禁规则”的工程闭环。

## 7. 一个最小对照实验：验证这些机制是否有效

### 7.1 实验设计

在测试环境中，让 AI 实现 4 个典型功能，每个功能都对应一类生产盲区：

| 任务 | 功能 | 注入的生产条件 |
| --- | --- | --- |
| T01 | 导出活跃用户报表 | 3000 万行的表、含非法 JSON 的历史数据 |
| T02 | 支付回调消费 | 同一条消息重复投递 3 次、乱序到达 |
| T03 | 库存扣减 | 100 个并发请求扣减同一商品 |
| T04 | 字段改名的数据库迁移 | 新旧版本同时运行、表中有历史数据 |

每个任务分两组运行：

- **A 组（只给需求）：** 只提供需求描述和代码仓库。
- **B 组（启用第一、二层）：** 额外提供生产画像和生产禁忌，并启用执行计划门禁、属性测试和并发测试。

每个任务每组重复 3 次，固定模型版本、工具集合和仓库版本。生成的代码在注入生产条件的测试环境中运行，统一用同一套检查脚本判定结果。

### 7.2 记录指标

| 指标 | 说明 |
| --- | --- |
| 通过率 | 在注入生产条件后，功能结果正确的比例 |
| 数据不一致次数 | 余额、库存、订单状态等不变量被破坏的次数 |
| 重复执行次数 | 同一请求或消息被处理多次的次数 |
| 门禁拦截次数 | B 组中，被执行计划门禁或测试在合并前拦下的问题数 |
| 误拦次数 | 门禁拦下但实际没有问题的次数 |
| 耗时 | 完成任务的时间，包括被拦截后的修改 |

**当前这里给出的是实验方案，不是实验结果。** 在实际运行并记录数据之前，不应声称这些机制已经降低了生产故障的发生率。

### 7.3 如何解释结果

- B 组通过率明显更高：第一、二层起了作用；进一步区分是生产画像让 AI 一开始就写对了，还是门禁在合并前拦下了问题。
- B 组门禁拦截很多，但最终通过率提升有限：AI 没有利用生产画像，需要检查画像是否被读取、内容是否清楚。
- 误拦次数很多：阈值过严，团队会开始绕过门禁，需要调整阈值或允许说明理由后放行。
- T02、T03 在两组都失败：只靠上下文和测试不够，需要第三层的数据库约束和幂等组件兜底。

## 8. 局限与权衡

**影子环境和流量回放成本高。** 需要和生产对齐的表结构、数据分布和网络配置，还要做好数据保护。不是每个服务都值得投入。

**门禁有误报。** 执行计划依赖统计信息，影子库与生产的偏差会导致误判；阈值过严，团队会开始想办法绕过。

**生产画像会过时。** 手工维护的画像很快就和生产对不上，必须由 CI 定时自动生成。

**暴露给 AI 的生产信息越多，泄露风险越大。** 只暴露元数据、统计信息和脱敏样本，观测接口只读。

**渐进发布拉长上线时间。** 金丝雀的每个阶段都要观察一段时间；对低风险变更，可以缩短观察时间。

**运行时护栏有误伤。** 语句超时和行数上限可能拦住少数合理的大查询，需要为这类场景提供经过审批的专用通道，而不是直接关掉护栏。

什么情况下可以放宽：

| 场景 | 建议 |
| --- | --- |
| 内部工具、低流量服务 | 保留第一层和硬超时，可以不做流量回放 |
| 非核心的只读接口 | 执行计划门禁和金丝雀发布即可 |
| 资金、库存、权限等核心链路 | 四层全部启用，并加上影子写校验 |
| 数据库结构变更 | 无论服务大小，都按“先扩展、再迁移、后收缩”执行 |

## 9. 常见问题诊断表

| 症状 | 可能原因 | 优先处理方式 |
| --- | --- | --- |
| 本地测试全绿，上线后慢查询拖垮数据库 | AI 不知道表的规模，CI 没有检查执行计划 | 生产画像写明表量级；CI 加执行计划门禁；数据库账号设置语句超时 |
| 线上出现解析异常或空指针 | 历史脏数据没被测试覆盖 | 属性测试和模糊测试；把线上异常固化为脱敏回归用例 |
| 改了接口后，下游老系统出错 | 破坏了隐式契约 | 契约测试；流量回放对比响应；规范中禁止改变已有字段的语义 |
| 重复扣款或库存超卖 | 缺少幂等和并发控制 | 唯一索引和 CHECK 约束兜底；提供幂等组件；并发和重复投递测试 |
| 发布期间部分请求失败 | 数据库变更不兼容旧版本 | 先扩展、再迁移、后收缩；迁移附带回滚脚本 |
| 一个慢接口拖垮整个服务 | 没有资源隔离 | 独立的线程池和连接池；熔断和降级 |
| 问题上线后很久才发现 | 全量发布，缺少指标对比 | 金丝雀发布和指标驱动的自动回滚 |
| 同类事故反复出现 | 复盘只修 Bug，没有产出约束 | 事故转规则，复盘模板中必须填写护栏产出 |

## 10. 经验总结

1. **最大的风险不是代码写不出来，而是上线就雪崩。** 根源是信息不对称：AI 看不到生产的状态、并发、脏数据和隐式依赖。
2. **先界定盲区。** 数据规模与分布、并发与时序、隐式契约、基础设施约束、业务不变量，五类盲区各有对应的手段。
3. **能暴露的，安全地左移给 AI。** 生产画像、只读脱敏的观测接入、约束代码化；但绝不直接交出生产数据。
4. **不能暴露的，用确定性护栏拦在发布前。** 执行计划门禁、流量回放、契约测试和属性测试，代替人工判断生产隐患。
5. **防不住的，用爆炸半径控制关在笼子里。** 默认 AI 代码一定会出错：硬超时、数据库约束、隔离熔断、渐进发布和自动回滚。
6. **数据库变更要兼容新旧两个版本。** 先扩展、再迁移、后收缩，每一步都能回退。
7. **把事故编译进系统。** 每次线上问题至少产出一条门禁规则、一个回归用例或一条规范，能写成规则的优先写成规则。
8. **按投入产出比分阶段推进。** 先立规矩、设硬底线，再建仿真、控发布，最后形成闭环。
