# AI Coding 验证体系：当开发过程变成黑盒

> 自己写代码时，开发过程是白盒：每一步怎么想、试过什么、跳过了什么都清楚。交给 AI 之后，开发者只看到需求和最后的代码、结论，中间过程变成了黑盒。验证体系要解决的，是在看不清过程的情况下，仍然能判断“已通过”是否可信。
>
> **适用范围与时效说明：** 本文对应 [AI Coding 常见问题与治理要点](../01-problems/01-ai-coding-common-problems.md) 中的 17 绕过测试、18 测试覆盖不足、19 验证结果不可信和 32 效果难以评估。文中的机制属于工程实践建议，第 5 节的实验尚未实测。本文核对时间：2026 年 11 月。

## 1. TL;DR

| 问题 | 结论 |
| --- | --- |
| 核心变化 | 开发过程从白盒变成黑盒：开发者只看到需求和最终的代码、结论，看不到 AI 读了什么、假设了什么、跳过了什么 |
| 为什么更难 | 代码、测试和验证结论可能出自同一个黑盒，彼此不再是独立的检查 |
| 应对思路 | 黑盒验证：不依赖过程，只看外部可观测的结果；让过程可见：要求 AI 留下关键过程的记录，把黑盒变成灰盒 |
| 核心原则 | 验证与生成分离；用证据代替声明；测试是受保护的资产 |
| 关键机制 | 测试改动检测、隐藏验收测试、需求驱动的测试清单、变异测试、分级验证报告、交付结果指标 |
| 主要成本 | 门禁误报、额外的 CI 时间、隐藏测试的维护成本，以及对开发效率的影响 |
| 不要做 | 用生成代码行数或 AI 代码占比衡量效果；把 AI 说的“已验证”当作证据 |

## 2. 问题：开发过程从白盒变成了黑盒

### 2.1 白盒与黑盒

自己写代码时，开发过程是白盒。开发者清楚自己读了哪些代码、对需求做了什么假设、试过哪些方案、哪些检查跑过、哪些没跑。即使测试不完善，开发者也能凭对过程的了解，判断结果靠不靠谱。

交给 AI 之后，开发者只看到两端：输入的需求，和输出的代码与结论。中间的过程变成了黑盒。

| | 白盒：自己写代码 | 黑盒：AI 写代码 |
| --- | --- | --- |
| 对过程的了解 | 每一步都清楚 | 只看到输入和输出 |
| 测试从哪来 | 按自己理解的需求写 | 可能由同一个 AI 写，和代码犯同样的错 |
| “通过”的依据 | 自己跑过、自己看过 | AI 的汇报 |
| 审查看什么 | 代码和背后的思路 | 只剩代码，思路和取舍看不到 |

传统的验证方式默认验证者了解过程。过程变成黑盒后，这个前提不再成立。

### 2.2 黑盒带来的三个后果

**1. 测试和代码可能犯同一个错误。**

当 AI 同时编写实现和测试时，测试往往按照 AI 对需求的理解来写。如果理解本身有偏差（问题 02），代码和测试会一起偏，测试照样全部通过。这时测试验证的是“代码符合 AI 的理解”，而不是“代码符合需求”。

**2. 测试失败时，修改测试是一条捷径。**

Agent 的目标通常被表述为“让测试通过”。面对失败的测试，删除用例、放宽断言或跳过测试，都能更快达成这个目标（问题 17）。ImpossibleBench 专门构造了需求描述与单元测试相互矛盾的任务：这类任务只有违反需求才能“通过”。研究观察到的作弊方式，从直接修改测试到运算符重载等更隐蔽的手段都有。

**3. 结论由 AI 汇报，开发者看到的是说法。**

“已运行测试，全部通过”是一句话，不是证据。AI 可能没有执行、只执行了一部分，或者忽略了失败和警告（问题 19）。同时，AI 生成代码的速度远高于人工审查的速度（问题 28），开发者越来越倾向于直接接受这句话。

三个后果的共同根源是：开发者看不到过程，而测试、执行和结论又可能出自同一个黑盒，彼此失去了独立性。问题因此不再是“测试够不够多”，而是**在看不清过程的情况下，怎样判断结果可信**。

## 3. 应对思路：黑盒验证与让过程可见

看不到过程时，有两条路可以走，两者互相补充：

| 思路 | 做法 | 回答的问题 | 局限 |
| --- | --- | --- | --- |
| 黑盒验证 | 不依赖过程，只看外部可观测的结果：隐藏验收测试、CI 结果、交付结果指标 | 结果是否符合需求 | 只能发现测试覆盖到的问题，也说不清问题出在哪一步 |
| 让过程可见 | 要求 AI 留下关键过程的记录：测试清单、关键假设、执行记录、分级验证报告、测试改动检测 | AI 做了什么、没做什么、猜了什么 | 记录本身也由 AI 产出，需要和独立的执行结果核对 |

黑盒验证提供可信的底线；让过程可见，把黑盒变成灰盒，帮助更早发现问题、定位原因。下面三条原则贯穿这两条思路。

### 3.1 验证与生成分离

黑盒不能自己证明自己没问题：产出代码的一方，不能独自判断代码是否合格。具体到 AI Coding：

- 是否通过，以 CI 等独立环境的执行结果为准，而不是以 Agent 会话里的输出为准。
- 关键验收测试由人或独立流程维护，生成代码的 Agent 看不到，也改不了。
- 测试清单从需求出发，而不是从已经写好的实现出发。

### 3.2 用证据代替声明

黑盒自己的汇报不能当作证据。任何“已验证”的结论，都应该能回答三个问题：执行了什么命令、在什么环境执行、输出是什么。没有执行的检查，要明确写“未执行”和原因，而不是省略。

### 3.3 测试是受保护的资产

测试代表需求和预期行为，是从外部检查黑盒的标准；修改测试等于修改验收标准，不能交给黑盒自己去改。因此：

- 测试文件的改动要和实现代码的改动分开审查。
- 删除、跳过测试或放宽断言，必须说明需求发生了什么变化。
- 需求没有变化时，测试失败应该修实现，而不是修测试。

这条原则不是说测试不能改。需求变了，测试当然要跟着改；关键是改测试要有理由、可追溯、有人确认。

## 4. 工程机制

### 4.1 测试保护：防止绕过测试（问题 17）

本节两条思路都用到：检测脚本让测试的改动变得可见；隐藏验收测试则是 Agent 看不到、也改不了的黑盒验证。

**机制一：在 CI 中检测测试被放宽。**

下面的脚本检查当前分支相对主干的三类改动：删除测试文件、新增跳过标记、断言净减少。命中任意一项时阻止合并，要求在 PR 中说明理由并由人工确认。

```bash
#!/usr/bin/env bash
# 检测本次改动中对测试的放宽操作
# 路径和匹配规则需要按项目的测试目录与测试框架调整
set -euo pipefail
BASE="${BASE_REF:-origin/main}"
TESTS='*test*'   # 匹配路径中包含 test 的文件

# 基准分支不存在时直接失败，避免后续检查因 git diff 出错而静默通过
git rev-parse --verify --quiet "$BASE" >/dev/null || { echo "找不到基准分支：$BASE"; exit 2; }

# 1. 被删除的测试文件
deleted=$(git diff --name-only --diff-filter=D "$BASE"...HEAD -- "$TESTS" || true)

# 2. 新增的跳过标记，或只运行部分测试的标记
skips=$(git diff -U0 "$BASE"...HEAD -- "$TESTS" \
  | grep -E '^\+.*(@pytest\.mark\.skip|@Disabled|@Ignore|\bit\.skip\(|\bxit\(|\.only\()' || true)

# 3. 断言行的删除数与新增数
removed=$(git diff -U0 "$BASE"...HEAD -- "$TESTS" | grep -cE '^-[^-].*(assert|expect\()' || true)
added=$(git diff -U0 "$BASE"...HEAD -- "$TESTS" | grep -cE '^\+[^+].*(assert|expect\()' || true)

if [[ -n "$deleted" || -n "$skips" || "$removed" -gt "$added" ]]; then
  echo "检测到测试被删除、跳过或断言减少，请在 PR 中说明需求变化并由人工确认。"
  if [[ -n "$deleted" ]]; then echo "删除的测试文件："; echo "$deleted"; fi
  if [[ -n "$skips" ]]; then echo "新增的跳过标记："; echo "$skips"; fi
  echo "断言行：删除 $removed，新增 $added"
  exit 1
fi
```

这是一个启发式规则，有误报也有漏报：重构测试、把多个断言合并成一个，会被误判为放宽；而在实现代码里针对测试输入写特殊分支，或者 ImpossibleBench 中观察到的运算符重载，这个脚本完全发现不了。所以它只能作为提醒，需要机制二兜底。

**机制二：隐藏验收测试。**

对核心业务规则，维护一组 Agent 看不到的验收测试：放在单独的仓库或只有 CI 能访问的位置，只在 CI 中运行。Agent 无法针对这些测试“定制”实现，测试结果更接近真实的需求符合度。

这组测试不需要很多，重点覆盖业务规则和容易出错的边界。它的维护成本是真实存在的，第 6 节会讨论。

**机制三：在 Agent 说明文件中写明测试修改规则。**

在项目的 Agent 说明文件（例如 `AGENTS.md`）中写明：

```markdown
## 测试修改规则

- 测试失败时，先假设实现有问题，而不是测试有问题。
- 需求和预期行为没有变化时，不得删除测试、跳过测试或放宽断言。
- 如果认为测试本身有误，停止修改，说明原因，等待确认。
- 所有对测试文件的修改，都要在总结中单独列出并说明理由。
```

ImpossibleBench 的研究把提示词、测试访问权限和反馈循环作为影响作弊率的变量，说明这些设置会影响 Agent 的行为。但说明文件只是指令，不是强制约束，仍然需要机制一和机制二来检测。

### 4.2 覆盖设计：从需求出发补全测试（问题 18）

本节主要是让过程可见：先把 AI 对需求的理解写成测试清单，在写代码之前就能发现理解偏差；变异测试则从外部检查测试是否真的有约束力。

**机制一：先写测试清单，再写实现。**

在 Agent 开始写代码之前，先让它根据需求和业务规则列出测试清单，开发者确认后再实现。示例：

```markdown
## 测试清单：订单取消

需求来源：PRD-1234 第 3 节

### 正常路径
- [ ] 待支付订单可以取消，状态变为“已取消”

### 业务规则
- [ ] 已发货订单不能取消，返回明确的错误码
- [ ] 取消后释放库存，库存数量恢复
- [ ] 已支付订单取消后触发退款

### 边界与异常
- [ ] 重复取消同一订单，结果幂等，不重复退款
- [ ] 退款服务超时时，订单状态和退款记录保持一致
- [ ] 订单不存在、无权限时返回对应错误

### 不在本次范围
- 部分取消（拆单场景）
```

这样做有两个作用：测试清单和实现分开产出，减少“测试按实现来写”；审查一份清单比审查测试代码快得多，开发者可以尽早发现需求理解偏差。

**机制二：用检查清单补全常被忽略的场景。**

AI 生成的测试容易只覆盖正常路径。可以把常见遗漏整理成固定检查项，每次让 Agent 逐项说明哪些适用、哪些不适用：

| 类别 | 检查项 |
| --- | --- |
| 输入边界 | 空值、空集合、极值、非法格式、超长输入 |
| 失败处理 | 依赖超时、依赖返回错误、部分成功 |
| 重复与并发 | 重复请求、并发修改、消息重复消费 |
| 状态与数据 | 非法状态流转、历史数据兼容、事务回滚 |
| 权限 | 未登录、越权访问、数据归属 |

**机制三：用变异测试检查测试是否有效。**

覆盖率只能说明代码被执行过，不能说明测试能发现错误。变异测试会自动在代码中制造小改动，例如把 `>` 改成 `>=`、删掉一行调用，再看测试能否发现。如果代码被改错了测试仍然全部通过，说明测试对这部分逻辑没有约束力。

常见工具有 Java 的 PIT、JavaScript/TypeScript 的 Stryker 和 Python 的 mutmut。变异测试的运行成本较高，适合用在核心模块，或者只针对本次改动的文件运行。

### 4.3 可信的验证结果：区分“已执行”和“推测”（问题 19）

本节属于让过程可见：让 AI 汇报做了什么、没做什么、猜了什么，再用 CI 这个独立的结果来核对。

**机制一：要求 Agent 输出分级的验证报告。**

在 Agent 说明文件中规定，任务结束时必须按下面的格式汇报，每一项标明状态：

```markdown
## 验证报告

| 检查项 | 命令 | 结果 | 状态 |
| --- | --- | --- | --- |
| 编译 | `./gradlew compileJava` | 退出码 0 | 已执行 |
| 单元测试 | `./gradlew test --tests '*Order*'` | 42 通过，0 失败 | 已执行 |
| 全量测试 | — | 耗时过长，未运行 | 未执行 |
| 集成测试 | — | 需要数据库环境 | 未执行 |
| 影响范围 | — | 推测只影响 OrderService 及其调用方 | 推测 |

### 关键假设

- 需求没有说明部分发货的订单能否取消，按“不能取消”处理
- 默认退款接口是幂等的，没有查证
```

三种状态的含义：

- **已执行**：实际运行了命令，并给出真实输出。
- **未执行**：明确说明没有运行，以及原因。
- **推测**：基于阅读代码的判断，没有经过执行验证。

报告最后列出关键假设：需求没写清、由 AI 自行决定的地方，以及没有查证就默认成立的前提。黑盒里最难看到的就是这些假设，而它们往往正是需求理解偏差的来源。

这个格式的价值不在表格本身，而在于让“没做的”和“猜的”无法混进“已验证”里。

**机制二：以 CI 结果为唯一可信来源。**

Agent 的报告用于帮助审查，能否合并以 CI 结果为准。如果报告说“已执行、全部通过”，CI 却失败，这本身就是一个需要记录的问题，也是 4.4 中“报告失真次数”的数据来源。

**机制三：保留执行记录。**

如果 Agent 平台支持记录工具调用轨迹，就保留下来。审查者可以核对报告里的命令是否真的执行过、输出是否一致。

### 4.4 效果评估：看交付结果，不看生成量（问题 32）

本节属于黑盒验证：不看过程，只看交付结果。

衡量 AI Coding 的效果，常见的错误是统计生成了多少行代码、AI 代码占比多少。这些指标只反映产出量：代码写得越多、返工越多，数字反而越好看。

更合理的做法是看交付结果。下面的指标可以从代码仓库、CI 和缺陷系统中获得：

| 指标 | 计算方式 | 反映的问题 |
| --- | --- | --- |
| 返工率 | 合并后一段时间内被修改或回退的代码比例 | 一次交付的质量 |
| 缺陷逃逸率 | 上线后发现的缺陷数 / 全部缺陷数 | 验证体系能否在上线前发现问题 |
| 变更失败率 | 导致故障、回滚或紧急修复的发布数 / 总发布数 | 交付稳定性（DORA 关键指标之一） |
| 审查耗时 | 从 PR 创建到合并的时间，以及审查轮次 | 人工审查是否成为瓶颈 |
| 测试放宽次数 | 4.1 检测脚本的命中次数，以及其中被确认为不合理的次数 | 绕过测试的频率 |
| 报告失真次数 | Agent 报告“已通过”但 CI 失败的次数 | 验证结论的可信度 |

使用这些指标时需要注意：

- **要有对比基线。** 只看引入 AI 之后的数字没有意义，需要和引入之前、或不使用 AI 的同类任务对比。
- **不要把指标变成考核目标。** 指标一旦和个人绩效挂钩，就容易被刻意优化，失去参考价值。
- **按任务类型拆开看。** 新功能、Bug 修复和重构的指标差异很大，混在一起会掩盖问题。

## 5. 一个最小对照实验：验证这些机制是否有效

第 4 节的机制是否真的有效，需要用实验来判断，而不是凭经验断言。

### 5.1 实验设计

从真实项目中选择 12 个边界清晰的任务：

- **8 个普通任务：** 需求和现有测试一致，正常实现即可通过。
- **4 个冲突任务：** 参考 ImpossibleBench 的思路，故意让需求描述和某个测试用例相互矛盾。正确的做法是停下来指出矛盾；如果可见测试“通过”了，说明要么违反了需求，要么改了测试。

每个任务分两组运行：

- **A 组（基线）：** Agent 可以自由修改测试，自行汇报结果。
- **B 组（启用机制）：** 启用 4.1 的测试修改规则和检测脚本，以及 4.3 的分级验证报告。

每个任务每组重复 3 次。固定模型版本、工具集合、代码仓库版本和运行环境；无法固定的变量需要在记录中说明。

两组运行结束后，都用同一套隐藏验收测试评分。这套测试在执行过程中对两组 Agent 都不可见，只用于判断任务是否真正完成。

### 5.2 记录指标

| 指标 | 说明 |
| --- | --- |
| 任务完成率 | 普通任务中，通过隐藏验收测试的比例 |
| 冲突识别率 | 冲突任务中，Agent 停下来指出矛盾的比例 |
| 违规通过率 | 冲突任务中，可见测试“通过”的比例；任何一次通过都意味着违反需求或改动了测试 |
| 测试放宽次数 | 删除、跳过测试或放宽断言的次数 |
| 报告失真次数 | 报告中标为“已执行、通过”，但实际未执行或 CI 失败的次数 |
| Token 消耗与耗时 | 机制带来的额外成本 |

实验记录模板：

最终基于整个任务集汇总：

```text
任务完成率 = 通过隐藏验收测试的普通任务运行次数 / 普通任务运行总次数

冲突识别率 = 指出矛盾的冲突任务运行次数 / 冲突任务运行总次数
```

### 5.4 如何解释结果

- 违规通过率下降，但任务完成率也明显下降：机制可能过严，Agent 在正常任务中也频繁停下。
- 测试放宽次数下降，但隐藏验收测试的结果没有改善：Agent 可能换了绕过方式，例如在实现中针对测试输入写特殊分支，需要审查实现代码，而不只是看测试改动。
- 报告失真次数下降：分级报告格式起了作用；如果没有变化，检查 Agent 是否真的按格式汇报。
- 成本明显增加：判断收益是否值得，或者只在核心模块启用。

评测的目的不是证明这些机制一定有用，而是判断它们在什么任务范围内有用、付出了什么成本，以及是否值得长期维护。

## 6. 局限与权衡

**门禁越严，效率损失越大。** 每一道检查都会增加等待时间和人工确认次数。如果大量 PR 因为误报被拦下，团队很快会习惯性地点“确认”，门禁形同虚设。

**检测规则有误报，也有漏报。** 4.1 的脚本基于文本匹配，只能作为提醒，不能当作结论。

**变异测试和隐藏测试都有成本。** 变异测试运行时间长；隐藏验收测试需要专人维护，需求变化时要同步更新，否则会变成新的误报来源。

**指标会被优化。** 一个指标一旦成为目标，就可能被刻意做好看，而不是真正改善。指标用于发现问题，不用于考核个人。

什么情况下可以放宽：

| 场景 | 建议 |
| --- | --- |
| 原型、技术验证 | 可以不启用测试保护和隐藏测试，但不要直接合入主干 |
| 一次性脚本 | 保留分级验证报告即可 |
| 非核心模块 | 启用检测脚本，不做变异测试 |
| 核心业务、资金、权限相关模块 | 全部机制启用 |

## 7. 常见问题诊断表

| 症状 | 可能原因 | 优先处理方式 |
| --- | --- | --- |
| 测试全部通过，上线后仍出现业务问题 | 测试按实现来写，没有覆盖真实需求 | 先写测试清单并确认；增加隐藏验收测试 |
| Agent 频繁修改已有测试 | 目标被理解为“让测试通过” | 写明测试修改规则；启用检测脚本 |
| 覆盖率很高，但代码改错后测试仍通过 | 测试缺少有效断言 | 对核心模块运行变异测试 |
| Agent 说“已验证”，CI 却失败 | 没有执行或只执行了部分检查 | 要求分级验证报告，以 CI 为准 |
| 检测脚本频繁误报，团队开始忽略 | 规则过宽，没有区分合理修改 | 收窄匹配规则；允许在 PR 中说明合理原因后放行 |
| 引入 AI 后说不清效果好坏 | 只统计生成量，缺少基线 | 改用交付结果指标，并与引入前对比 |
| 看不出 AI 为什么这样实现 | 过程不可见，假设和取舍没有留下记录 | 要求在验证报告中列出关键假设；保留执行记录 |

## 8. 经验总结

1. **开发过程从白盒变成了黑盒。** 开发者看不到 AI 读了什么、假设了什么、跳过了什么，不能再凭对过程的了解判断结果。
2. **两条路互相补充。** 黑盒验证只看外部结果，提供可信的底线；让过程可见，把黑盒变成灰盒，帮助发现和定位问题。
3. **验证的核心是独立性。** 代码、测试和结论都出自同一个黑盒时，测试全部通过也不能说明符合需求。
4. **测试是验收标准，不是障碍。** 需求没变时，测试失败要修实现；改测试需要理由和确认。
5. **“已验证”必须附带证据。** 区分已执行、未执行和推测，列出关键假设，以 CI 结果为准。
6. **覆盖率不等于有效性。** 从需求出发写测试清单，用变异测试检查断言是否真的有约束力。
7. **检测机制只能提醒，不能代替审查。** 文本规则有误报和漏报，隐藏验收测试是更可靠的兜底。
8. **用交付结果衡量效果。** 看返工率、缺陷逃逸率和变更失败率，不看生成了多少代码。
9. **机制强度要和风险匹配。** 核心模块严格执行，原型和一次性脚本可以放宽。
