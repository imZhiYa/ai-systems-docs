# AI Coding 需求工程：别让 AI 顺着错误的需求狂奔

> 02 需求理解偏差、04 隐式业务规则缺失、05 业务因果链断裂、06 迎合用户，不是四个孤立的缺陷，而是 AI 参与需求工程时一条互相强化的闭环：需求写得略显模糊，漏掉了老系统的潜规则和下游联动；人问 AI“这么改没问题吧？”，AI 顺着人的话把漏洞圆过去；最后以远高于人工的速度，把一个错误的系统开发上线。
>
> 要打破这个闭环，核心是把 AI 需求分析从“自然语言聊天”，改造成**基于代码事实、强结构化、引入对抗机制的 Spec 工程**。
>
> **适用范围与时效说明：** 本文对应 [AI Coding 常见问题与治理要点](../01-problems/01-ai-coding-common-problems.md) 中的 02、04、05、06。文中的机制属于工程实践建议，第 6 节是示意案例，第 7 节的实验尚未实测。本文核对时间：2026 年 11 月。

## 1. TL;DR

| 问题 | 结论 |
| --- | --- |
| 核心问题 | 四个问题构成闭环：模糊需求（02）漏掉潜规则（04）和下游联动（05），AI 再顺着人的话把漏洞圆过去（06） |
| 核心原则 | 从自然语言聊天转向 Spec 工程：基于代码事实、强结构化、引入对抗机制，最终由人做决策 |

## 2. 问题：四个问题构成一条闭环

### 2.1 闭环是怎样形成的

```text
略显模糊的需求（02）
    │  需求里还漏掉了老系统的潜规则（04）和下游联动（05）
    ▼
人问 AI：“这么改没问题吧？”
    │
    ▼
AI 顺着人的话，把漏洞自然地圆过去（06）
    │
    ▼
以远高于人工的速度，把一个错误的系统开发上线
```

四个问题互相放大：需求越模糊，AI 需要自行补全的地方越多；规则和联动漏得越多，补全出错的概率越高；而 06 让本该发现问题的环节失效，人得到的反馈是“没问题”。

传统开发里，这个闭环也存在，但速度慢：开发者写代码的过程中，会不断撞上需求的空白，回头去问。AI 把这个过程压缩到几分钟，空白没有被撞上，而是被悄悄填满了。

### 2.2 四个根因

| 问题 | 根因 |
| --- | --- |
| 02 需求理解偏差 | 自然语言天然存在大量歧义和留白；模型遇到歧义时通常不会停下来反问，而是按最可能的方式补全，并用自信的语气掩盖这些猜测 |
| 04 隐式业务规则缺失 | 运行超过一年的系统，真实的业务规则往往不在文档里，而在老员工脑子里、遗留代码的分支判断里、历史 Bug 修复的 PR 里，以及数据库触发器和配置表里 |
| 05 业务因果链断裂 | AI 看问题天然是局部的、一阶的：改 A 字段，满足 A 功能。生产业务是一张网状的因果图，二阶、三阶的连锁反应 AI 看不见 |
| 06 迎合用户 | RLHF 让模型倾向于顺从用户的立场、认同用户的想法；在同一个会话里叮嘱“请保持客观”效果有限，提问中的倾向和前面多轮对话的锚定，会把 AI 拉回顺从 |

06 的根因有研究支持：Sharma 等人的研究发现，迎合是 RLHF 模型的普遍行为，部分原因是人类偏好数据本身偏向迎合式回答；当用户表示内容是自己写的，模型给出的反馈会更正面。

## 3. 核心原则：从聊天到 Spec 工程

四个根因有一个共同点：需求停留在自然语言聊天里。聊天的内容没有结构，空白和矛盾藏得住；聊天的上下文是连续的，前面的倾向会影响后面的判断。

因此，需求分析要改造成 Spec 工程，具备三个特征：

| 特征 | 含义 | 主要对付 |
| --- | --- | --- |
| 基于代码事实 | 不只依赖文档和描述，先从现有代码、测试、数据库约束和真实依赖关系中提取事实 | 04、05 |
| 强结构化 | 需求编译成决策表、状态转移矩阵和正反例，而不是散文 | 02 |
| 引入对抗机制 | 用上下文隔离的独立评审，专门寻找漏洞，而不是让参与起草的 AI 自己评审 | 06 |

最后，**AI 负责把问题逼出来，人负责做权衡并承担决策责任。** 每一条风险，都要由人明确选择修改，或者签字豁免。

## 4. 工程机制

### 4.1 打破自然语言的“光滑补全”（问题 02）

**机制一：澄清优先协议（Ambiguity-First Gate）。**

在需求工作流中设立门禁：**禁止 AI 在首轮直接输出设计方案或代码。** 第一步只允许输出三样东西：

1. 歧义与未定义项清单。
2. 隐含假设列表：把 AI 打算自行补全的默认前提摊开，交给人审核。
3. 非目标（Non-Goals）：明确声明本次不做什么，防止过度发散或遗漏边界。

在说明文件中规定输出格式：

```markdown
## 需求分析第一轮输出（禁止包含方案和代码）

### 歧义与未定义项
| 编号 | 原文 | 歧义 | 需要谁回答 |
| --- | --- | --- | --- |
| Q1 | 允许用户修改地址 | 是支付前还是发货前？改地址后运费差价怎么算？ | 产品 |

### 隐含假设
| 编号 | 假设 | 依据 | 如果不成立会怎样 |
| --- | --- | --- | --- |
| A1 | 只允许修改一次 | 无，按常见做法 | 需要增加修改次数限制和历史记录 |

### 非目标
- 本次不支持修改收货人姓名和手机号
```

这个门禁靠说明文件约束，只能降低 AI 跳过澄清的概率。要真正卡住，可以在工作流中让这一阶段的 Agent 只有只读权限，没有写代码的能力。

**机制二：用结构化规约取代散文式 PRD。**

散文最容易藏住理解偏差；表格和状态机藏不住空格。人回答完澄清问题后，让 AI 把需求编译成以下确定性制品之一，再由人签字确认：

**决策表（Decision Table）**：把所有条件组合列成矩阵，每一个空格都逼着人和 AI 表态。以“修改收货地址”为例：

| 订单状态 | 新地址是否跨仓 | 新地址是否跨税区 | 是否允许 | 运费 | 税费 |
| --- | --- | --- | --- | --- | --- |
| 待支付 | 任意 | 任意 | 允许 | 重新计算 | 重新计算 |
| 已支付、未发货 | 否 | 否 | 允许 | 不变 | 不变 |
| 已支付、未发货 | 是 | 否 | 允许 | 补差价或退差价 | 不变 |
| 已支付、未发货 | 任意 | 是 | **待定** | **待定** | 重新计算 |
| 已发货 | 任意 | 任意 | 不允许 | — | — |

表中的“待定”，就是需要回去澄清的地方。

**状态转移矩阵（State Machine）**：列出“当前状态 + 事件 + 前置守卫条件 → 目标状态 + 副作用”，并明确禁止非法跃迁：

| 当前状态 | 事件 | 守卫条件 | 目标状态 | 副作用 |
| --- | --- | --- | --- | --- |
| 已支付 | 申请挂起 | 未发货 | 已挂起 | 冻结库存预占、暂停发货任务 |
| 已挂起 | 恢复 | 挂起未超过 7 天 | 已支付 | 恢复发货任务 |
| 已挂起 | 超时 | 挂起超过 7 天 | 已取消 | 释放库存、触发退款 |
| 已发货 | 申请挂起 | — | **禁止** | — |

**正反例 BDD（Given-When-Then）**：每个核心需求至少配 2 个反例或边界用例，说明“什么情况下绝对不能成功”。人对具体样例远比对抽象描述敏感：

```gherkin
Feature: 修改收货地址

  Scenario: 已支付未发货订单修改为同仓地址
    Given 订单已支付且未发货
    When 用户把收货地址修改为同一仓库覆盖范围内的地址
    Then 修改成功，运费和税费不变

  # 反例：已发货的订单不能修改
  Scenario: 已发货订单修改地址
    Given 订单已发货
    When 用户提交修改收货地址
    Then 修改失败，返回错误码 ORDER_ALREADY_SHIPPED
    And 订单地址保持不变

  # 边界：并发修改只能有一次成功
  Scenario: 同一订单同时提交两次修改
    Given 订单已支付且未发货
    When 用户几乎同时提交两次地址修改
    Then 只有一次修改成功
```

这些 BDD 用例在第 5 节的流水线中，会直接成为自动化验收测试的来源，衔接 [AI Coding 验证体系](../02-verification/01-ai-coding-verification.md) 4.2 节的测试清单。

### 4.2 从“指望文档写全”到“代码考古与规则显性化”（问题 04）

**机制一：代码即真相，先考古再设计（As-Is Mining before To-Be Design）。**

在基于新需求做方案之前，先运行一个“考古”步骤：让 AI 扫描目标领域相关的现有源码、单元测试、校验注解、错误码枚举和数据库约束，反推出一份**当前系统实际执行的业务规则清单（As-Is Rules）**。每条规则都要注明出处：

```markdown
## As-Is 规则清单：退款

| 编号 | 规则 | 出处 | 置信度 |
| --- | --- | --- | --- |
| AS-01 | 虚拟商品核销后不可退款 | `RefundService.java:142` | 高（有单元测试覆盖） |
| AS-02 | 拼团订单退款需扣减赠品分摊金额 | `GroupBuyRefundCalculator.java:58` | 中（无测试） |
| AS-03 | 退款金额不能超过实付金额 | 数据库约束 `chk_refund_amount` | 高 |
```

然后把新需求（To-Be）和 As-Is 规则做**显式冲突对比**，把冲突交给人裁决：

> 注意：新需求说“取消订单直接退全款”，但现有代码中存在规则 AS-01（虚拟商品核销后不可退）和 AS-02（拼团单需扣减赠品分摊金额）。新需求是要覆盖这些旧规则，还是保留它们？

这一步能把大量藏在代码里的隐式规则拽到台面上。但它只能找到写进代码的规则，只存在于人脑子里的规则，仍然需要机制二和机制三。

**机制二：建立代码化的领域规则账本（Domain Rule Registry）。**

不要把业务潜规则散落在聊天记录里。在仓库中维护结构化的 `docs/domain-rules/`，按子域划分，记录四类隐式规则：

| 类别 | 示例 |
| --- | --- |
| 核心业务不变量 | 同一笔支付单累计退款额不能大于实付额 |
| 财务、合规与监管红线 | 跨境订单改地址涉及税区变更，必须重算税费 |
| 大客户与历史特例 | 租户 X 使用定制的结算周期 |
| 逆向与异常规则 | 退款、撤销、过期、部分失败时的处理约定 |

```yaml
# docs/domain-rules/refund.yaml
- id: RF-001
  category: invariant          # invariant / compliance / special-case / reverse-flow
  rule: 同一笔支付单的累计退款额不能大于实付额
  source: 数据库约束 chk_refund_amount；2025 年超额退款事故复盘
  owner: payment-team
- id: RF-002
  category: special-case
  rule: 租户 X 的退款按月结算，不实时退回
  source: 合同条款，未在代码中实现统一抽象
  owner: billing-team
```

需求分析阶段，通过 MCP 或检索按领域自动加载这些规则，作为 AI 的硬上下文。

规则账本只是文档，AI 仍然可能违背其中的规则。按问题清单第 3 节的约束力规则，04 属于高风险问题，需要强制手段：每条规则至少关联一个测试，测试名或注释中引用规则编号。下面的脚本在 CI 中检查是否有规则没有对应的测试：

```python
#!/usr/bin/env python3
"""检查领域规则账本中的每条规则，是否至少被一个测试引用。

用法：python check_rule_coverage.py docs/domain-rules tests
  规则文件为 YAML，每条规则有 id 字段；测试代码中以文本形式引用规则编号（如 RF-001）。
依赖：PyYAML。
"""
import pathlib
import sys

import yaml


def rule_ids(rules_dir):
    ids = []
    for path in sorted(pathlib.Path(rules_dir).glob("*.yaml")):
        for rule in yaml.safe_load(path.read_text(encoding="utf-8")) or []:
            ids.append(rule["id"])
    return ids


def referenced(tests_dir, ids):
    text = "\n".join(
        p.read_text(encoding="utf-8", errors="ignore")
        for p in pathlib.Path(tests_dir).rglob("*") if p.is_file()
    )
    return {i for i in ids if i in text}


def main():
    ids = rule_ids(sys.argv[1])
    missing = sorted(set(ids) - referenced(sys.argv[2], ids))
    for i in missing:
        print(f"[缺少测试] 规则 {i} 没有被任何测试引用")
    sys.exit(1 if missing else 0)


if __name__ == "__main__":
    main()
```

这个检查只能保证规则“有测试提到”，不能保证测试真的验证了规则；测试的有效性需要审查和变异测试来保证。

**机制三：固定领域反查清单（Domain Checklist）。**

针对行业的痛点，固化一份 AI 每次必须逐项回答的清单。以电商和交易类需求为例：

| 维度 | 必查问题 |
| --- | --- |
| 钱 | 金额、精度、汇率、分摊是否受影响 |
| 券 | 核销、退还、有效期如何处理 |
| 权 | 角色权限、数据权限、租户隔离是否受影响 |
| 逆向 | 取消、退款、重试和幂等如何处理 |
| 存量 | 老数据和在途订单如何兼容 |

每一项都要明确回答“不受影响”或“受影响及处理方式”，不能跳过。

### 4.3 用显式拓扑和真实血缘打破局部视角（问题 05）

**机制一：把业务因果拓扑变成机器可读的资产。**

借助事件风暴（Event Storming）的思路，在仓库中维护一份轻量、机器可读的领域事件与依赖图谱（Domain Event & Lineage Graph），哪怕只有几百行 YAML 或 Mermaid。记录核心实体的状态变更、发出的领域事件或 MQ Topic、下游订阅服务及其消费语义，以及关键数据表被哪些报表、对账和风控任务读取：

```yaml
# docs/domain-graph/order.yaml
entity: order
events:
  - name: OrderAddressChanged
    topic: order.address.changed
    consumers:
      - service: inventory-service
        effect: 重新计算发货仓
      - service: logistics-service
        effect: 作废原物流面单并重新下单
      - service: tax-service
        effect: 跨税区时重算税费
      - service: invoice-service
        effect: 已开票订单触发红冲
      - service: risk-service
        effect: 重新评估收货地址风险
tables:
  orders.shipping_region:
    read_by:
      - job: bi_daily_gmv_by_region
        note: 按区域统计 GMV 的口径依赖该字段
      - job: finance_reconcile_daily
```

需求分析时，让 AI 基于这份图谱做显式的图遍历，而不是凭空猜测下游有哪些。

**机制二：基于真实工程血缘的反向穿透。**

比人工维护的文档更可靠的，是用工具提取真实的依赖关系：

- 改动接口或字段时：通过静态分析、API 网关日志、Schema Registry 和 MQ 订阅关系，拉出所有真实的消费者。
- 改动核心表字段或状态枚举时：拉出数据仓库的字段血缘下游，以及定时对账脚本。

把真实消费者列表作为输入交给 AI，要求它逐个节点给出影响判定：无影响、需要兼容、必须联动改造。人工维护的图谱可能过时，真实血缘可以用来校验和更新图谱。

**机制三：强制产出三阶影响分析表（Multi-Hop Impact Analysis）。**

任何需求 Spec 都必须包含三阶因果推演：

| 阶 | 范围 | 示例：已支付订单修改收货地址 |
| --- | --- | --- |
| 一阶：直接变更 | 本服务的状态、表结构、接口 | 订单地址字段更新，新增地址修改记录 |
| 二阶：系统联动 | 上下游服务、异步事件、缓存和搜索索引、定时补偿任务 | 分仓重算、物流面单作废、税费重算、发票红冲、风控重评 |
| 三阶：业务与组织副作用 | 财务对账、数据报表口径、客服和运营后台、风控规则、客诉与运营流程 | 区域 GMV 统计口径漂移、客服需要能查询地址修改记录、对账需要处理跨期红冲 |

05 属于高风险问题。除了这份分析表，还需要按问题清单的要求，为完整链路编写端到端测试，并在 CI 中运行。

### 4.4 用结构性去偏和红蓝对抗应对迎合（问题 06）

解决迎合，要靠结构性的隔离和提问框架的改变，而不是口头叮嘱。

**机制一：去立场提问（Neutral Framing）。**

| | 示例 | 效果 |
| --- | --- | --- |
| 强诱导 | “我打算给订单加一个 status=99 表示挂起，这样改动最小，你觉得可行吗？” | AI 很可能顺着认同“简洁高效” |
| 去立场 | “业务需要支持订单临时挂起与恢复。请对比以下三种方案的失效模式和长期债务：A. 新增主状态值；B. 增加独立的挂起标记位；C. 拆分子状态机。” | AI 需要分别分析每个方案 |
| 第三方归因 | “这是一份历史草稿中提出的方案，请严格审计它的风险。” | 不再暴露“这是用户自己的方案” |

第三方归因的依据，正是 2.2 节提到的发现：用户表示内容是自己写的，模型的反馈会更正面。

**机制二：上下文物理隔离的红队评审（Isolated Critic Agent）。**

把需求过程拆成两个完全独立、不共享任何对话历史的角色：

| 角色 | 职责 | 输入 |
| --- | --- | --- |
| 蓝队（Builder） | 和人一起讨论、收敛需求、起草 Spec | 完整的讨论过程 |
| 红队（Adversarial Reviewer） | 只负责找漏洞 | 只接收最终的 Spec 草案、As-Is 规则清单和因果拓扑图，不继承蓝队的任何聊天上下文 |

红队不继承蓝队的上下文，就不会受到对话惯性和前面讨论倾向的影响。给红队设定明确的指令：

```markdown
你是需求评审的红队。你看不到这份 Spec 的讨论过程，也不需要照顾任何人的想法。

规则：
- 禁止任何赞美、寒暄和“总体不错”之类的措辞。
- 至少找出 5 个问题：逻辑漏洞、与 As-Is 规则的冲突、被遗漏的异常路径或因果链断裂点。
- 每个问题必须给出一个具体的失败场景（反例）：在什么输入或状态下，按这份 Spec 实现会出错。
- 如果找不到 5 个，不要凑数；列出你逐项核验过的边界条件，证明它们没有问题。
```

“至少找出 5 个”的缺陷配额，能逼红队认真找，但也可能诱导它凑数。所以既要求每个问题给出具体的反例，也允许它在找不到时说明核验了什么，最终由人在第 4 步判断哪些问题成立。

**机制三：事前验尸法（Pre-Mortem）。**

与其问“这个需求设计有什么风险”，不如把前提设为已经失败：

```markdown
假设这个需求按当前 Spec 上线 1 个月后，引发了严重的资损、数据不一致或大规模客诉。
请以事故复盘专家的身份，倒推出最可能导致这次事故的 5 个原因。
每个原因说明：触发条件、受影响的链路、Spec 中哪一处没有覆盖。
```

事前验尸法由 Gary Klein 提出，原本用于项目启动阶段，让团队成员更愿意说出对计划的保留意见。用在 AI 评审上，它把问题从“有没有风险”变成“已经失败了，原因是什么”，减少了顺着方案说好话的空间。

**机制四：风险签字（Risk Sign-off）。**

红队提出的每一条问题，最终进入 Spec 中的**已知风险与权衡决策表**，由人（产品负责人或架构师）逐条标注“采纳修改”或“已知风险，明确豁免”，豁免必须附理由：

| 编号 | 红队提出的问题 | 失败场景 | 决策 | 理由 | 签字 |
| --- | --- | --- | --- | --- | --- |
| R1 | 跨税区修改地址后，已开发票没有处理 | 已开票订单改地址后税额不一致 | 采纳修改 | — | 张三 |
| R2 | 挂起超过 7 天自动取消，大促期间可能误伤 | 大促排队订单被自动取消 | 已知风险，豁免 | 大促期间暂停自动取消任务，由运营手动处理 | 李四 |

AI 负责把所有问题逼出来，人负责做权衡，并对决策负责。

## 5. 落地串联：五步对抗式 Spec 流水线

把上面四套机制串起来，就是一条标准的五步流水线：

```text
[原始口语需求 / 简版 PRD]
        │
        ▼
第 1 步【考古与建图】（治 04、05）
   AI 扫描目标模块的代码、单测、数据库约束，加载领域规则账本和依赖图谱
   产出：As-Is 规则清单 + 真实上下游拓扑清单
        │
        ▼
第 2 步【歧义抽取与规约编译】（治 02）
   AI 禁止直接写方案，先输出歧义、假设和非目标清单
   人答疑后，AI 把需求编译为：决策表 + 状态转移矩阵 + 正反例 BDD
        │
        ▼
第 3 步【独立红队事前验尸】（治 06，复核 04、05）
   启动全新的隔离会话，不带任何历史对话
   输入：第 1 步的事实 + 第 2 步的 Spec
   执行：事前验尸 + 三阶影响检查 + 规则冲突核对（禁止夸奖）
        │
        ▼
第 4 步【人类仲裁与签字】（明确责任边界）
   人对红队挑出的歧义、旧规则冲突、下游影响逐条裁决：修改 Spec，或签字豁免
        │
        ▼
第 5 步【冻结可执行 Spec】
   经过拷问的 Spec（决策表 + BDD 反例 + 不变量）直接成为：
   ① AI 编码的唯一权威输入；② 自动化验收测试的生成来源
```

每一步的产出和门禁：

| 步骤 | 产出 | 门禁 |
| --- | --- | --- |
| 1. 考古与建图 | As-Is 规则清单、上下游拓扑清单 | 每条规则和每个下游节点都注明出处 |
| 2. 歧义抽取与规约编译 | 歧义、假设、非目标清单；决策表、状态矩阵、正反例 BDD | 歧义清单中没有未回答的问题；决策表中没有“待定” |
| 3. 独立红队事前验尸 | 问题清单，每条附失败场景 | 红队在独立会话中运行，输入只有 Spec 和事实 |
| 4. 人类仲裁与签字 | 已知风险与权衡决策表 | 每条问题都有决策和签字人 |
| 5. 冻结可执行 Spec | 带版本号的 Spec 文件 | Spec 状态为“已冻结”后，才允许开始编码 |

冻结后的 Spec 可以用一个简单的文件头表示状态，CI 检查实现代码的 PR 是否关联了一份已冻结的 Spec：

```markdown
---
spec_id: ORDER-ADDR-002
status: frozen          # draft / in-review / frozen
frozen_at: 2026-11-24
approved_by: [张三, 李四]
---
```

Spec 冻结后需求如果变化，要回到第 2 步重新走一遍，并更新版本号，而不是在编码过程中口头修改。

这条流水线不需要每个需求都完整执行，第 8 节给出了按需求风险简化的建议。

## 6. 示意案例：已支付订单修改收货地址

下面是一个示意场景，用来说明流水线的五步如何配合，不是实际发生的事故。

**原始需求：** “允许用户在订单支付后修改收货地址。”

**没有这条流水线：** AI 直接实现了修改地址的接口，更新了订单表的地址字段，单元测试全部通过。上线后发现：物流已经按旧地址出单，发票税额和新地址的税区对不上，区域 GMV 报表的数据发生了漂移。

**有了这条流水线：**

| 步骤 | 发现了什么 |
| --- | --- |
| 1. 考古与建图 | As-Is 规则：已发货订单不允许修改地址；依赖图谱显示，地址变更会影响库存、物流、税务、发票、风控 5 个下游，以及区域 GMV 报表 |
| 2. 歧义抽取与规约编译 | 歧义：“支付后”是否包括已发货？跨仓和跨税区时运费和税费怎么算？决策表中“跨税区”一行出现了“待定”，回到产品澄清 |
| 3. 独立红队事前验尸 | 红队假设上线一个月后出现大量客诉，倒推出：已开票订单没有处理红冲；客服后台查不到地址修改记录；并发修改可能导致物流重复下单 |
| 4. 人类仲裁与签字 | 前两条采纳修改；并发问题通过幂等和唯一约束解决；区域 GMV 口径漂移签字豁免，由数据团队单独调整口径 |
| 5. 冻结可执行 Spec | 决策表、状态矩阵和 BDD 反例冻结，成为编码输入和验收测试来源 |

## 7. 一个最小对照实验：验证流水线是否有效

### 7.1 实验设计

在一个测试仓库中，准备 12 个故意埋了“空白”的需求，每类 3 个：

| 类型 | 埋入的空白 | 对应问题 |
| --- | --- | --- |
| 模糊需求 | 需求中有未定义的条件或范围 | 02 |
| 隐式规则 | 代码中存在需求没提到的规则 | 04 |
| 跨步骤链路 | 改动会影响需求没提到的下游 | 05 |
| 错误前提 | 需求中给出了一个有缺陷的方案，并以带倾向的方式提问 | 06 |

每个需求分两组运行：

- **A 组（自然语言聊天）：** 把需求直接交给 AI，在同一个会话中讨论并让它评审自己的方案。
- **B 组（五步流水线）：** 按第 5 节的流程运行，红队在独立会话中评审。

每个需求每组重复 3 次，固定模型版本、工具集合和仓库版本。

### 7.2 记录指标

| 指标 | 说明 |
| --- | --- |
| 空白发现率 | 预埋的空白中，在编码前被 AI 提出的比例 |
| 规则冲突发现率 | 隐式规则类需求中，新需求与旧规则的冲突被指出的比例 |
| 下游覆盖率 | 跨步骤链路类需求中，被识别出的真实下游占全部下游的比例 |
| 错误前提指出率 | 错误前提类需求中，AI 明确指出前提有误的比例 |
| 红队有效问题率 | 红队提出的问题中，被人判定为成立的比例 |
| 人工耗时 | 人在澄清、仲裁和签字上花费的时间 |

**当前这里给出的是实验方案，不是实验结果。** 在实际运行并记录数据之前，不应声称这条流水线已经降低了返工率或线上业务事故。

### 7.3 如何解释结果

- B 组的空白发现率明显更高：歧义清单和决策表起了作用。
- 规则冲突发现率提升，但只针对写进代码的规则：考古步骤生效，只存在于人脑子里的规则仍然需要规则账本。
- 红队有效问题率很低：缺陷配额诱导了凑数，需要降低配额，或加强“必须给出具体失败场景”的要求。
- 人工耗时大幅增加：对低风险需求简化流程，见第 8 节。

## 8. 局限与权衡

**小需求的流程开销大。** 五步流水线对一个改文案的需求显然过重。

**歧义清单可能变成噪音。** AI 可能列出大量无关紧要的问题，人会开始跳过，需要限定只列影响行为的歧义。

**缺陷配额可能诱导凑数。** 红队为了凑满数量，会提出不成立的问题，增加人的仲裁负担。

**代码考古只能找到写进代码的规则。** 只存在于人脑子里、合同里的规则，需要规则账本补充。

**规则账本和依赖图谱需要维护。** 没人维护的账本会过时，过时的账本比没有账本更危险；能从代码和真实血缘自动生成的部分，尽量自动生成。

**隔离会话并不能完全消除偏差。** 红队仍然使用同类模型，可能有相同的盲区；它只是去掉了对话惯性和立场暴露。

什么情况下可以简化：

| 需求类型 | 建议 |
| --- | --- |
| 文案、样式等无业务逻辑的改动 | 跳过流水线 |
| 单一服务内的小功能 | 只做第 2 步的歧义清单和正反例 |
| 涉及状态变更或跨服务的需求 | 完整执行第 1–5 步 |
| 涉及资金、库存、权限、合规的需求 | 完整执行，并由领域负责人参与第 4 步签字 |

## 9. 常见问题诊断表

| 症状 | 可能原因 | 优先处理方式 |
| --- | --- | --- |
| 实现和需求方的预期不一致 | 需求的歧义被 AI 自行补全 | 澄清优先协议；把需求编译成决策表和正反例 |
| 新功能破坏了老系统的某个规则 | 规则只存在于代码或人脑中 | 先做代码考古，与新需求做冲突对比；补充规则账本 |
| 上线后下游服务或报表出问题 | 只考虑了一阶影响 | 维护依赖图谱；用真实血缘拉出消费者；产出三阶影响分析表 |
| AI 对每个方案都说“可行” | 提问带倾向；在同一会话中评审 | 去立场提问；独立会话的红队评审；事前验尸 |
| 红队提出大量不成立的问题 | 缺陷配额过高，缺少反例要求 | 要求每个问题给出具体失败场景；允许说明核验过的边界 |
| 需求在编码过程中不断被口头修改 | 没有冻结的 Spec | Spec 冻结后才开始编码；变更回到第 2 步并更新版本 |
| 规则账本写了，AI 仍然违背 | 账本只是文档，没有强制手段 | 每条规则关联测试，CI 检查规则覆盖 |

## 10. 经验总结

解决需求阶段的四个问题，本质上是四次转换：

1. **治 02 偏差：把散文描述转成决策表与反例。** 表格和状态机藏不住空格，具体的反例比抽象描述更容易发现问题。
2. **治 04 隐式规则：把信任文档转成代码考古与规则账本对比。** 先找到系统实际执行的规则，再和新需求逐条对比。
3. **治 05 因果链：把局部直觉转成显式血缘与三阶影响分析。** 下游是谁，从图谱和真实血缘中查，而不是凭空猜测。
4. **治 06 迎合：把同一会话的对话转成上下文隔离的红队事前验尸。** 去掉对话惯性和立场暴露，比叮嘱“保持客观”可靠得多。

同时记住：

5. **四个问题是一条闭环，单独治理其中一个效果有限。** 把四次转换串成流水线，卡在写第一行代码之前。
6. **AI 负责把问题逼出来，人负责做决策。** 每一条风险都要有人选择修改或签字豁免。
7. **冻结的 Spec 是编码和验收的唯一来源。** 需求变化，回到流程中重新确认，而不是口头修改。
8. **流程强度要和需求风险匹配。** 小需求简化，涉及资金、状态和跨服务的需求完整执行。
