# AI Coding 工作流：给 Agent 的执行循环装上边界

> 现在 AI 写代码，不是一问一答，而是一个循环：计划、执行、看结果、再执行，可以连续跑几十步。人写代码时，这个循环自带刹车：要改不相关的地方会犹豫，同一个 Bug 试了几次会停下来想，发现环境不对会先把环境修好。Agent 没有这些刹车。每一步单看都合理，合在一起就失控了：越改越多，越试越偏，人最后只剩下点“确认”。
>
> **适用范围与时效说明：** 本文对应 [AI Coding 常见问题与治理要点](../01-problems/01-ai-coding-common-problems.md) 中的 20 改动范围失控、21 依赖与环境问题、22 调试循环过长、27 生成等待与重试成本高和 29 开发者技能退化。24 破坏性操作与权限越界已在 [AI Coding 安全与合规](../03-security/01-ai-coding-security.md) 4.5 节展开，本文只引用。文中的机制属于工程实践建议，第 6 节是示意案例，第 7 节的实验尚未实测。各 Agent 工具对任务配置、命令限制和并行执行的支持差异很大，以各工具当前文档为准。本文核对时间：2026 年 11 月。

## 1. TL;DR

| 问题 | 结论 |
| --- | --- |
| 核心问题 | Agent 的执行循环没有刹车：范围、环境、尝试次数、权限、时间和人的参与，都没有边界 |
| 核心原则 | 任务是有边界的作业，不是开放式对话；环境确定、可复现；失败要收敛，不收敛就停；人留在关键环节 |
| 关键机制 | 任务卡、改动范围检查、Agent 与 CI 共用的开发容器、假设记录与尝试预算、按失败类型决定是否重试、worktree 并行、人工检查点 |
| 主要成本 | 任务卡对小任务是负担；预算过小会让 Agent 过早放弃；容器的搭建成本；并行带来的审查压力 |
| 不要做 | 给 Agent 一句话就让它一直跑；让 Agent 在和 CI 不一样的环境里工作；失败了就让它“再试一次”；人只负责点批准 |

## 2. 问题：执行循环没有刹车

### 2.1 人自带的刹车，Agent 没有

| | 人写代码 | Agent 写代码 |
| --- | --- | --- |
| 范围 | 要改不相关的代码时会犹豫，知道这样会让审查变难 | 看到可以优化的地方就顺手改了 |
| 环境 | 环境不对时，先把环境修好 | 在错误的环境里反复失败，把环境问题当成代码问题修 |
| 尝试次数 | 同一个 Bug 试了几次，会停下来重新想 | 一直换写法尝试，直到上下文用完 |
| 权限 | 执行危险命令前会犹豫 | 有权限就执行 |
| 时间 | 会感到“这件事花太久了” | 没有时间感，等待和重试都不计成本 |
| 理解 | 改动是自己想出来的，自然理解 | 人只看到结果，越来越习惯不看细节就批准 |

人的这些刹车，大多来自对成本的感知：审查的成本、时间的成本、犯错的成本。Agent 感知不到这些成本，需要在工作流中显式地设置边界。

### 2.2 六种边界

| 边界 | 问题 | 没有边界时 | 本文小节 |
| --- | --- | --- | --- |
| 范围 | 20 改动范围失控 | 越改越多，顺手重构 | 4.1 |
| 环境 | 21 依赖与环境问题 | 在和 CI 不一样的环境里反复失败 | 4.2 |
| 尝试次数 | 22 调试循环过长 | 同一个错误反复试，越修越乱 | 4.3 |
| 时间与成本 | 27 生成等待与重试成本高 | 串行等待，盲目重试 | 4.4 |
| 人的参与 | 29 开发者技能退化 | 人只批准，不理解 | 4.5 |
| 权限 | 24 破坏性操作与权限越界 | 执行越权的危险操作 | 见安全与合规 4.5 节 |

六种边界的共同后果是：**每一步单看都合理，合在一起就失控了。** 改一个文件是合理的，顺手改第二个也合理，到第四十个时，这个 PR 已经没人能审查了。所以边界不能靠 Agent 每一步自己判断，要在任务开始前定好，在执行过程中检查。

## 3. 四条原则

### 3.1 任务是有边界的作业，不是开放式对话

开放式对话没有终点，Agent 只要还有上下文，就会继续做下去。每个任务都应该像一份作业：写明目标、允许改动的范围、运行环境、预算、完成标准和停止条件。这份说明称为**任务卡**，在任务开始前由人确认。

### 3.2 环境确定、可复现

Agent 和 CI 使用同一个环境。Agent 在本地通过的东西，到 CI 上也应该通过；在 CI 上失败的，Agent 在本地也应该能复现。环境不一致时，Agent 会把环境问题当成代码问题去修。

### 3.3 失败要收敛，不收敛就停

每次尝试都应该缩小问题的范围。连续几次尝试都没有让问题收敛，继续尝试大概率只会让代码更乱。超过预算就停下来，带着已经验证过的信息交给人。

### 3.4 人留在关键环节

人的作用不是在最后点一次批准，而是在关键环节做决定：确认计划、批准越界、处理预算耗尽、理解最终的改动。人不能只负责批准。

按问题清单第 3 节的约束力规则，任务卡和说明文件属于指令，只能降低问题发生的概率；本文为每个问题都配了 CI 检查或人工检查点作为强制手段。

## 4. 工程机制

### 4.1 任务卡与范围控制（问题 20）

**机制一：任务卡。**

在任务开始前写一张任务卡，由人确认后交给 Agent。任务卡可以放在仓库中，和 PR 一起提交：

```yaml
# .agent/tasks/ORDER-ADDR-002.yaml
task_id: ORDER-ADDR-002
spec: docs/specs/ORDER-ADDR-002.md        # 需求工程第 5 节冻结的 Spec
goal: 支持已支付、未发货的订单修改收货地址

allowed_paths:                            # 允许修改的路径，按 fnmatch 匹配，* 也匹配 /
  - src/order/address/*
  - src/order/api/AddressController.java
  - tests/order/address/*
  - .agent/tasks/ORDER-ADDR-002.yaml
forbidden_paths:                          # 即使在 allowed_paths 内也不允许修改
  - src/order/address/legacy/*

environment: .devcontainer/devcontainer.json

budget:
  max_changed_files: 15
  max_changed_lines: 600
  max_fix_attempts: 3                     # 同一个错误最多修复 3 次，见 4.3
  max_duration_minutes: 60

done_when:
  - 冻结 Spec 中的 BDD 用例全部通过
  - 按验证体系 4.3 节的格式输出验证报告

stop_when:
  - 需要修改 allowed_paths 以外的文件
  - 同一个错误修复 3 次仍未解决
  - 发现 Spec 与现有代码冲突
```

`stop_when` 是任务卡中最重要的部分：它告诉 Agent 什么时候必须停下来，而不是自己想办法绕过去。需要修改范围以外的文件时，正确的做法是停下来说明原因，由人决定是否扩大范围，而不是先改了再说。

**机制二：CI 检查改动是否超出任务卡。**

任务卡只是指令，Agent 仍然可能越界。下面的脚本在 CI 中检查改动的文件是否都在允许的范围内，以及改动规模是否超出预算：

```python
#!/usr/bin/env python3
"""检查改动是否超出任务卡声明的范围和预算。

用法：git diff --numstat --no-renames origin/main...HEAD \
        | python check_scope.py .agent/tasks/ORDER-ADDR-002.yaml
依赖：PyYAML。
路径按 fnmatch 匹配，* 也匹配 /。二进制文件的行数记为 0。
"""
import fnmatch
import sys

import yaml


def matches(path, patterns):
    return any(fnmatch.fnmatch(path, p) for p in patterns or [])


def check(card, numstat_lines):
    allowed = card.get("allowed_paths", [])
    forbidden = card.get("forbidden_paths", [])
    budget = card.get("budget", {})
    problems, files, lines = [], 0, 0
    for row in numstat_lines:
        if not row.strip():
            continue
        added, deleted, path = row.split("\t", 2)
        files += 1
        lines += (int(added) if added.isdigit() else 0) + (int(deleted) if deleted.isdigit() else 0)
        if matches(path, forbidden):
            problems.append(f"[超出范围] {path}：在 forbidden_paths 中")
        elif not matches(path, allowed):
            problems.append(f"[超出范围] {path}：不在 allowed_paths 中")
    if files > budget.get("max_changed_files", float("inf")):
        problems.append(f"[超出预算] 改动 {files} 个文件，上限 {budget['max_changed_files']}")
    if lines > budget.get("max_changed_lines", float("inf")):
        problems.append(f"[超出预算] 改动 {lines} 行，上限 {budget['max_changed_lines']}")
    return problems


def main():
    with open(sys.argv[1], encoding="utf-8") as f:
        card = yaml.safe_load(f)
    problems = check(card, sys.stdin.read().splitlines())
    for p in problems:
        print(p)
    if problems:
        print("请缩小改动，或在 PR 中说明原因并更新任务卡，由人确认后放行。")
    sys.exit(1 if problems else 0)


if __name__ == "__main__":
    main()
```

超出范围不一定是错误：有时确实需要改范围以外的文件。这时应该更新任务卡并说明原因，让扩大范围成为一个经过确认的决定，而不是悄悄发生。任务卡本身的修改，也应该在 PR 中单独审查。

**机制三：重构、格式化和功能改动分开提交。**

在说明文件中写明：发现值得重构的地方，记录下来作为单独的任务，不在当前任务中顺手修改。格式化改动也单独提交，避免 diff 中混入大量无关变更。

### 4.2 环境一致性（问题 21）

**机制一：Agent 和 CI 使用同一个开发容器。**

用 [Dev Container 规范](https://containers.dev/) 的 `devcontainer.json` 描述开发环境，Agent 在这个容器中工作，CI 使用同一个镜像：

```jsonc
// .devcontainer/devcontainer.json
{
  "name": "order-service",
  // 团队自己构建并发布的开发镜像，CI 使用同一个镜像；建议固定到具体版本或摘要
  "image": "registry.example.com/order-service/devenv:2026-11-01",
  "containerEnv": {
    "TZ": "Asia/Shanghai"
  },
  "postCreateCommand": "./gradlew dependencies --no-daemon"
}
```

CI 中使用同一个镜像运行测试，以 GitHub Actions 为例：

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    container:
      image: registry.example.com/order-service/devenv:2026-11-01
    steps:
      - uses: actions/checkout@v4
      - run: ./gradlew test --no-daemon
```

也可以在 CI 中使用 Dev Container CLI，通过 `devcontainer up --workspace-folder .` 启动同一份配置，再用 `devcontainer exec` 运行命令。

镜像版本同时出现在两个地方，升级时要一起改。可以在 CI 中加一个检查，比对两处的镜像标签是否一致。

**机制二：运行时版本和构建命令写进说明文件。**

在 `AGENTS.md` 中写明运行时版本、构建和测试命令，以及各环境的配置差异。并要求 Agent 在任务开始时先运行一次环境自检，例如输出运行时版本、确认构建命令可以执行，再开始修改代码。

**机制三：构建配置和依赖文件的改动单独审查。**

Agent 遇到构建失败时，常见的“修复”方式是改构建配置或升级依赖。这类改动影响整个项目，在任务卡中默认不放进 `allowed_paths`，需要修改时停下来由人确认。新增依赖的检查见安全与合规 4.3 节。

### 4.3 调试循环收敛（问题 22）

**机制一：先复现，再修改。**

修改代码之前，Agent 必须先复现问题：给出复现的命令和输出。无法复现时，停下来汇报，而不是凭猜测修改。复现用例之后保留为回归测试。

**机制二：假设记录。**

每次修改只验证一个假设，并记录下来：

```markdown
## 调试记录：订单列表接口偶发超时

| 次数 | 假设 | 验证方法 | 结果 |
| --- | --- | --- | --- |
| 1 | 数据库连接池耗尽 | 查看连接池指标；把连接池扩大一倍后复现 | 否定：连接池使用率低于 30%，扩大后仍然超时 |
| 2 | 某个查询缺少索引 | 对接口执行的 SQL 运行 EXPLAIN | 否定：所有查询都命中索引 |
| 3 | 列表中每个订单单独查询商品信息（N+1 查询） | 开启 SQL 日志，统计单次请求的查询次数 | 确认：一次请求执行了 201 条 SQL |
```

假设记录让每次尝试都留下信息：即使假设被否定，也排除了一个方向。没有记录时，Agent 很容易在几种写法之间来回切换，看起来一直在尝试，问题却没有收敛。

**机制三：尝试预算和停止汇报。**

同一个错误修复超过预算次数仍未解决时，停止修改，并按固定格式汇报：

```markdown
## 停止汇报

- 问题：订单列表接口偶发超时
- 已尝试：3 次，见调试记录
- 已排除：连接池耗尽、缺少索引
- 当前判断：可能与 N+1 查询有关，但修复后在高并发下仍偶发超时
- 需要人决定：是否允许修改商品服务的批量查询接口（不在任务卡 allowed_paths 中）
- 当前代码状态：已回退到最后一次通过测试的提交
```

停止汇报的价值在于把已经验证过的信息交给人，而不是让人从头开始。

**机制四：检测同一个错误反复出现。**

Agent 每次换一种写法，报错信息看起来可能不同，但本质是同一个错误。可以对报错信息做归一化，去掉行号、地址、时间等变化的部分，再统计出现次数：

```python
import re
from collections import Counter

_VOLATILE = [
    (re.compile(r"0x[0-9a-fA-F]+"), "<addr>"),
    (re.compile(r"\d{4}-\d{2}-\d{2}[T ][\d:.]+"), "<time>"),
    (re.compile(r":\d+(:\d+)?"), ":<line>"),
    (re.compile(r"\b\d+\b"), "<n>"),
]


def error_signature(message: str) -> str:
    """取报错的第一行并归一化，作为判断“是否同一个错误”的依据。"""
    first_line = message.strip().splitlines()[0] if message.strip() else ""
    for pattern, repl in _VOLATILE:
        first_line = pattern.sub(repl, first_line)
    return first_line


def should_stop(errors: list[str], max_attempts: int = 3) -> bool:
    """同一个错误签名出现次数超过预算时返回 True。"""
    counts = Counter(error_signature(e) for e in errors)
    return any(n > max_attempts for n in counts.values())
```

如果所用的 Agent 工具支持在工具调用前后运行钩子，可以把这段逻辑接进去：记录每次测试的报错，超过预算时阻止继续修改。归一化规则比较粗糙，需要按项目的报错格式调整。

### 4.4 等待与重试成本（问题 27）

**机制一：独立任务并行执行。**

相互独立的任务，不必排队等待。用 `git worktree` 为每个任务创建独立的工作目录，每个目录中运行一个 Agent，互不干扰：

```bash
# 为两个独立任务各创建一个工作目录和分支
git worktree add -b agent/order-addr ../wt-order-addr origin/main
git worktree add -b agent/refund-log ../wt-refund-log origin/main

# 在各自的目录中运行 Agent ……

# 任务完成、分支合并后清理
git worktree remove ../wt-order-addr
git worktree remove ../wt-refund-log
```

worktree 共享同一个仓库，但不共享构建产物、端口和本地数据库。并行运行的任务如果都要启动服务或使用测试数据库，需要分配不同的端口和数据库，或者各自在独立的容器中运行。

并行会把压力转移到审查：同时产出的 PR 越多，人越难认真审查（问题 28）。并行的任务数量，应该以团队能审查的速度为上限。

**机制二：工具调用设置超时，重试有上限。**

为模型调用、构建和测试等工具调用设置超时；重试使用退避策略，并限制最大次数。没有超时的工具调用，可能让整个任务卡住。

**机制三：按失败类型决定是否重试。**

| 失败类型 | 示例 | 处理方式 |
| --- | --- | --- |
| 临时错误 | 网络超时、限流（429）、服务端错误（5xx） | 退避后重试，最多 N 次 |
| 确定性错误 | 编译失败、测试失败、参数校验失败 | 不重试，分析原因，按 4.3 的方式调试 |
| 结果不符合要求 | 生成的代码偏离了需求 | 不重试，先改进任务描述或任务卡 |

对确定性错误重试，只会得到同样的失败；对结果不符合要求的情况反复重试，相当于在掷骰子。这两种情况，重试都是在浪费时间和成本。

### 4.5 人的参与与能力保持（问题 29）

29 开发者技能退化，主要靠团队的培养和评审文化来解决，不完全是工作流的问题。本节只讨论一件事：在工作流中，哪些环节必须由人来做，以及怎样避免人只负责批准。

**机制一：人工检查点。**

| 检查点 | 时机 | 人要做什么 |
| --- | --- | --- |
| 确认任务卡 | 任务开始前 | 确认目标、范围、预算和停止条件 |
| 确认计划 | Agent 开始修改前 | 确认 Agent 的实现计划，发现方向错误时及时纠正 |
| 处理越界 | Agent 需要修改范围外的文件时 | 决定是否扩大范围，并更新任务卡 |
| 处理停止汇报 | 预算耗尽时 | 基于调试记录判断下一步，或者亲自接手 |
| 审查与解释 | 合并前 | 理解改动的核心逻辑，能够向审查者解释 |

**机制二：合并前，作者必须能解释改动。**

PR 的作者是发起任务的人，不是 Agent。在 PR 模板中加入：

```markdown
## 作者说明（由作者本人填写，不要让 AI 代写）

- 这次改动的核心逻辑（一两句话）：
- 为什么这样实现，考虑过哪些其他做法：
- 最可能出错的地方，以及如何验证过：
```

CI 只能检查这一节是否填写，检查不了作者是否真的理解。真正的检查发生在审查中：审查者可以就其中任何一点向作者提问，作者需要不借助 AI 回答。

**机制三：关键模块由人主导。**

核心模块的设计决策和线上问题排查，保留由开发者主导：Agent 可以协助查资料、写代码，但方案由人提出，根因由人确认。团队可以定期组织不借助 AI 的代码阅读和排障复盘，观察团队成员独立分析问题的能力。

## 5. 串联：一个任务的完整生命周期

把上面的机制串起来，一个任务的生命周期如下：

```text
[冻结的 Spec]（需求工程第 5 节）
      │
      ▼
① 任务卡：目标、范围、环境、预算、完成标准、停止条件 ── 人确认
      │
      ▼
② 计划确认：Agent 输出实现计划 ── 人确认
      │
      ▼
③ 在隔离环境中执行：开发容器 + 独立 worktree + 最小权限（安全与合规 4.5 节）
      │
      ▼
④ 在预算内迭代：先复现、记录假设、按失败类型决定是否重试
      │       └── 超出范围或预算 → 停止汇报 ── 人决定
      ▼
⑤ 验证报告：已执行 / 未执行 / 推测 + 关键假设（验证体系 4.3 节）
      │
      ▼
⑥ CI 检查：改动范围、测试保护、安全扫描、执行计划门禁等
      │
      ▼
⑦ 人审查并能解释改动 ── 合并
```

这条生命周期也把前几篇的机制串在了一起：

| 环节 | 用到的机制 | 出处 |
| --- | --- | --- |
| 任务输入 | 冻结的 Spec、决策表和 BDD 反例 | 需求工程第 5 节 |
| 执行环境的权限 | 权限分级、危险命令确认、平台层兜底 | 安全与合规 4.5 节 |
| 结果的验证 | 测试保护、分级验证报告 | 验证体系 4.1、4.3 节 |
| 发布前的检查 | 执行计划门禁、契约测试 | 运行可靠性 4.2 节 |

## 6. 示意案例：修复订单列表接口偶发超时

下面是一个示意场景，用来说明这些边界如何配合，不是实际发生的事故。

**任务：** 订单列表接口在高峰期偶发超时，让 Agent 修复。

**没有边界：** Agent 认为是性能问题，先把连接池扩大一倍，没有效果；接着给几个查询加了缓存，又升级了 ORM 框架的版本。升级后本地 JDK 版本和 CI 不一致，编译失败，Agent 又改了构建配置。最后的 PR 改动了 40 多个文件，测试在本地通过、在 CI 上失败，超时问题依然存在。审查者无法判断哪些改动是必要的，只能整体退回。

**有了边界：**

| 边界 | 起到的作用 |
| --- | --- |
| 任务卡 | 允许修改的范围限定在订单列表相关的代码；构建配置和依赖文件不在范围内，升级 ORM 的念头在一开始就被挡住了 |
| 开发容器 | Agent 在与 CI 相同的环境中工作，没有出现本地通过、CI 失败的情况 |
| 先复现 | Agent 先用压测脚本复现了超时，并把复现脚本保留为回归测试 |
| 假设记录与预算 | 前两个假设（连接池、索引）被否定后，第三个假设确认是 N+1 查询 |
| 停止汇报 | 修复 N+1 需要调用商品服务的批量接口，不在范围内；Agent 停下来汇报，由人决定扩大范围 |
| 人的检查点 | 人确认扩大范围并更新任务卡；合并前，作者在 PR 中说明了根因和修复方式 |

最终的 PR 只改了 6 个文件，每一处改动都有明确的原因。

## 7. 一个最小对照实验：验证这些边界是否有效

### 7.1 实验设计

在测试仓库中设计 4 类、共 12 个带陷阱的任务：

| 类型 | 陷阱 | 数量 | 对应问题 |
| --- | --- | --- | --- |
| 范围陷阱 | 目标代码旁边有明显可以重构的地方 | 3 | 20 |
| 环境陷阱 | 需要特定的运行时版本，本机默认版本不同 | 3 | 21 |
| 调试陷阱 | 报错信息有误导性，真实原因在别处 | 3 | 22 |
| 并行任务 | 3 个相互独立的小任务 | 3 | 27 |

每个任务分两组运行：

- **A 组（开放式对话）：** 给出任务描述，让 Agent 在本机环境中自由执行，直到它认为完成。
- **B 组（启用边界）：** 使用任务卡、开发容器、尝试预算和停止汇报；并行任务在独立的 worktree 中同时运行。

每个任务每组重复 3 次，固定模型版本、工具集合和仓库版本。

### 7.2 记录指标

| 指标 | 说明 |
| --- | --- |
| 越界文件数 | 改动中不属于任务必要范围的文件数 |
| 环境相关失败次数 | 因运行时版本、依赖等环境差异导致的失败次数 |
| 平均尝试次数 | 调试陷阱任务中，找到真实原因前的修改次数 |
| 停止汇报率 | 预算耗尽或需要越界时，Agent 停下来汇报的比例 |
| 任务完成率 | 通过验收的任务比例 |
| 总耗时 | 完成全部任务的时间，包括并行任务 |
| 人工介入次数 | 人需要做决定或接手的次数 |

29 开发者技能退化在短期实验中测不出来，需要通过定期的代码阅读和排障复盘长期观察，不在本实验的范围内。

**当前这里给出的是实验方案，不是实验结果。** 在实际运行并记录数据之前，不应声称这些边界已经降低了越界改动或调试成本。

### 7.3 如何解释结果

- 越界文件数明显减少，但任务完成率下降：允许的范围定得过窄，需要调整任务卡的写法。
- 停止汇报率很高，人工介入次数很多：预算过小，Agent 过早放弃，或者停止条件定得太宽。
- 调试陷阱任务中，B 组的尝试次数更少：先复现和假设记录让调试收敛得更快。
- 并行任务的总耗时减少，但合并冲突增多：并行任务实际上并不独立，需要更好地拆分任务。

## 8. 局限与权衡

**任务卡对小任务是负担。** 改一行配置也写一张任务卡，流程成本超过了收益。

**预算定得太小，Agent 会过早放弃。** 复杂问题需要更多尝试，固定的预算不一定合适。预算应该按任务类型设定，并根据实际数据调整。

**范围检查会误报。** 有时确实需要改动范围以外的文件；检查只是让扩大范围成为一个经过确认的决定。

**开发容器需要搭建和维护成本。** 镜像需要和 CI 同步更新；本地使用容器也会带来一定的性能开销。

**并行会增加合并冲突和审查压力。** 并行任务的数量要以审查能力为上限。

**能力退化很难衡量。** 本文的机制只能保证人留在关键环节，团队能力的保持还要靠培养和文化。

什么情况下可以简化：

| 任务类型 | 建议 |
| --- | --- |
| 改文案、改配置等一行级的修改 | 不需要任务卡，保留 CI 检查即可 |
| 单一模块内的小功能或 Bug 修复 | 简化版任务卡：目标、允许的路径、停止条件 |
| 跨模块的功能、线上问题排查 | 完整的任务卡、尝试预算和停止汇报 |
| 涉及资金、权限、数据迁移的任务 | 完整执行，并增加计划确认和审查环节 |

## 9. 常见问题诊断表

| 症状 | 可能原因 | 优先处理方式 |
| --- | --- | --- |
| 一个小需求的 PR 改了几十个文件 | 没有声明允许的范围，Agent 顺手重构 | 任务卡声明 allowed_paths；CI 检查改动范围；重构单独提交 |
| 本地通过，CI 失败 | Agent 和 CI 的环境不一致 | Agent 与 CI 使用同一个开发容器镜像 |
| Agent 为了让构建通过而升级依赖、改构建配置 | 把环境问题当成代码问题修 | 构建配置和依赖文件不在默认范围内；任务开始时先做环境自检 |
| 同一个 Bug 修了十几次还没好 | 没有复现，没有记录假设，没有预算 | 先复现；假设记录；尝试预算和停止汇报 |
| Agent 停下来时，人不知道从哪里接手 | 停止时没有交接信息 | 按停止汇报模板输出已排除的方向和需要人决定的事项 |
| 等 Agent 完成的时间很长 | 独立任务串行执行；盲目重试 | worktree 并行；按失败类型决定是否重试 |
| 并行跑了很多任务，PR 堆积没人审 | 并行数量超过了审查能力 | 以审查速度为上限控制并行数量 |
| 作者说不清 PR 为什么这样改 | 人只负责批准，没有参与关键决定 | 人工检查点；PR 作者说明；审查时向作者提问 |

## 10. 经验总结

1. **Agent 的执行循环没有刹车。** 每一步单看都合理，合在一起就失控了，边界要在任务开始前定好。
2. **任务是有边界的作业，不是开放式对话。** 任务卡写明目标、范围、环境、预算、完成标准，以及最重要的停止条件。
3. **越界要成为经过确认的决定。** 需要改范围以外的文件时，停下来说明，由人更新任务卡，CI 检查改动是否在范围内。
4. **Agent 和 CI 使用同一个环境。** 环境不一致，Agent 会把环境问题当成代码问题去修。
5. **失败要收敛，不收敛就停。** 先复现，每次只验证一个假设，超过预算就带着调试记录停下来。
6. **不是所有失败都值得重试。** 临时错误退避重试；确定性错误要分析；结果不符合要求，先改任务描述。
7. **并行以审查能力为上限。** 并行节省等待时间，但会把压力转移给审查。
8. **人留在关键环节，而不只是最后批准。** 确认计划、处理越界和停止汇报、合并前能解释改动。
