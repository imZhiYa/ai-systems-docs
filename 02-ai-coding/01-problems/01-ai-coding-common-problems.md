## 1. 背景与目标

AI Coding 正在改变软件开发方式。AI 已经参与需求理解、代码生成、测试编写、问题排查和代码重构等环节。但代码生成能力的提升，并不意味着软件交付质量能够同步提升。

在真实项目中，AI 可能出现需求理解偏差、上下文丢失、跨模块分析不足、重复建设已有能力等问题。即使生成的代码能够通过局部测试，也不代表它符合整体架构约束和真实业务要求。

这些问题不仅与模型能力有关，还涉及上下文管理、工程约束、质量验证、开发流程和生产环境治理。

因此，AI Coding 面临的核心问题不只是**如何让 AI 生成代码，而是如何让 AI 可靠地参与整个软件工程交付过程**。

本文从真实软件工程视角整理 AI Coding 中常见的问题，建立统一的问题分类，为后续工程治理和实践方案提供基础。

> 说明：本文问题清单基于个人开发实践与公开讨论归纳，尚未经过系统化统计验证；各问题的发生频率和严重程度因项目与工具而异。

## 3. 具体问题

以下每个问题统一从三个维度描述：**问题描述**说明问题本身，**典型表现**列举开发中可观察到的现象，**工程影响**说明其对交付和系统造成的影响。

### 3.1 理解与上下文问题

这一类问题关注 AI 是否能够获取必要上下文，正确理解用户需求、项目结构和业务规则。

#### 01. 上下文丢失（Context Loss）

**问题描述**

AI 在持续开发过程中，无法完整保留之前的需求、技术决策、代码约束和任务进度，导致后续生成内容偏离已有约定。

**典型表现**

- 忘记之前确认的业务规则和技术方案。
- 重复询问已经提供过的信息。
- 多轮修改后，前后实现出现冲突。
- 上下文压缩或会话切换后，丢失关键任务信息。

**工程影响**

增加重复沟通和人工纠正成本，导致实现偏差，降低持续开发的稳定性。

#### 02. 需求理解偏差（Requirement Misunderstanding）

**问题描述**

AI 没有准确理解用户的真实需求，将自然语言描述错误地转换为技术实现，导致最终交付结果与业务预期不一致。

**典型表现**

- 只理解需求表面描述，没有识别真实业务目标。
- 遇到模糊需求时直接猜测，而不是澄清。
- 忽略需求中的前置条件、限制和验收标准。
- 实现了用户没有要求的功能。

**工程影响**

造成需求返工、功能偏差和额外开发成本，严重时可能影响核心业务流程。

#### 03. 跨文件与跨模块理解不足（Cross-Module Understanding）

**问题描述**

AI 主要关注当前文件或局部代码，缺乏对整个项目结构、模块依赖、调用链和数据流的完整理解。

**典型表现**

- 修改一个接口时，没有检查上下游调用方。
- 修改公共方法时，没有识别其他模块的依赖。
- 只关注当前模块，没有分析跨服务影响。
- 忽略配置文件、数据库结构和外部接口的关联。

**工程影响**

容易引入隐藏的兼容性问题和连锁故障，扩大代码变更的影响范围。

#### 04. 隐式业务规则缺失（Implicit Business Rules）

**问题描述**

真实业务中存在大量没有明确写入需求文档的隐式规则，AI 无法仅凭局部代码或简单需求描述准确识别这些约束。

**典型表现**

- 忽略订单状态之间的合法流转关系。
- 没有识别重复提交、重复操作等业务约束。
- 忽略权限、数据归属和业务边界。
- 没有考虑特殊业务场景和历史兼容规则。

**工程影响**

可能生成符合语法和技术规范、但违反业务规则的代码，造成数据错误和业务异常。

#### 05. 业务因果链断裂（Business Causality Gap）

**问题描述**

AI 能够理解单个业务操作，却无法完整识别多个业务事件之间的依赖关系、执行顺序和因果约束。

**典型表现**

- 无法完整梳理订单、库存、支付和物流之间的业务关系。
- 忽略事件触发顺序和前置条件。
- 没有识别跨系统操作需要满足的业务一致性要求（如支付成功后订单最终必须变为已支付）。
- 只实现单个接口，没有考虑完整业务链路。

**工程影响**

容易产生状态不一致、重复执行、数据丢失和业务流程异常等问题。

### 3.2 代码生成质量问题

这一类问题关注 AI 生成代码的正确性、规范性、复用能力、健壮性和长期可维护性。

#### 06. API 幻觉与版本错位（API Hallucination & Version Mismatch）

**问题描述**

AI 依据训练数据中的 API 知识生成代码，而没有查证项目实际使用的依赖版本，可能使用不存在的 API、错误的方法签名，或与当前版本不匹配的接口。

**典型表现**

- 调用不存在的类、方法或配置项。
- 使用其他版本才支持的 API。
- 生成与当前框架版本不兼容的代码。
- 错误理解第三方 SDK 的使用方式。

**工程影响**

导致编译失败、运行异常和反复调试，增加依赖升级与兼容性处理成本。

#### 07. 过度工程化（Over-Engineering）

**问题描述**

AI 在实现简单需求时，可能引入不必要的抽象层、设计模式、接口和组件，导致实现复杂度超过实际业务需要。

**典型表现**

- 简单逻辑被拆分为多个无必要的类。
- 引入不必要的设计模式和通用框架。
- 为单一场景设计过度通用的扩展机制。
- 增加多层封装，却没有带来实际收益。

**工程影响**

增加代码理解、测试和维护成本，使系统复杂度持续上升。

#### 08. 编码规范与项目约定不一致（Inconsistent Conventions）

**问题描述**

AI 生成代码时没有充分遵循项目现有的编码规范和实现习惯，导致代码库内部写法不一致。

**典型表现**

- 命名方式和现有代码不一致。
- 异常处理、日志记录和返回结构不统一。
- 没有遵循项目已有的分层规范。
- 同一业务场景出现多种实现方式。

**工程影响**

降低代码可读性和一致性，增加团队协作、代码审查和后期维护成本。

#### 09. 代码重复生成与已有能力重复建设（Duplicate Implementation）

**问题描述**

项目中已经存在可复用的工具类、公共组件、业务服务或基础设施能力，但 AI 没有充分检索和识别已有实现，而是重新创建相同或相似的功能。

**典型表现**

- 项目已有日期、字符串、集合等工具类，AI 仍然重新编写。
- 已有统一的 HTTP 客户端或 Redis 操作封装，AI 又创建新的实现。
- 不同模块重复实现相同的业务逻辑。
- 没有复用已有公共组件，而是增加新的工具类或辅助方法。
- 同一功能存在多个相似实现，逐渐形成重复代码。

**工程影响**

造成代码冗余、能力重复建设和维护成本增加。相同功能出现多个实现后，容易产生行为不一致、修复不同步和技术债累积等问题。

#### 10. 代码正确性不足（Incorrect Code Generation）

**问题描述**

AI 生成的代码在语法和局部逻辑上看似正确，但实际业务逻辑存在错误，或者没有覆盖完整的执行路径。

**典型表现**

- 条件判断存在遗漏或逻辑错误。
- 数据计算和状态更新不符合业务预期。
- 边界条件处理不完整。
- 局部实现正确，但组合后产生逻辑冲突。

**工程影响**

容易产生隐蔽的业务缺陷，增加问题定位成本，甚至导致生产数据异常。

#### 11. 代码健壮性不足（Insufficient Robustness）

**问题描述**

AI 生成代码时容易优先关注正常执行路径，而忽略异常场景、资源管理和系统边界条件。本问题关注代码层面的异常与资源处理；系统层面的故障恢复见 33。

**典型表现**

- 缺少必要的异常处理。
- 忽略空值、超时和非法输入。
- 资源没有正确释放。
- 重试逻辑缺少次数限制或退避策略。
- 对外部依赖缺少合理的失败处理。

**工程影响**

降低系统在异常情况下的稳定性，容易引发资源泄漏、请求堆积和故障扩散。

### 3.3 安全、合规与验证风险

这一类问题关注 AI 生成代码的安全与合规风险，以及测试和验证过程是否真实可信。

#### 12. 安全漏洞（Security Vulnerabilities）

**问题描述**

AI 在生成代码时可能忽略系统安全边界，没有充分考虑身份认证、权限控制、数据校验和敏感信息保护。

**典型表现**

- 存在 SQL 注入、命令注入等风险。
- 缺少接口权限校验。
- 存在越权访问或敏感数据泄露。
- 将密钥、Token 等敏感信息写入代码。
- 不安全地处理用户输入和外部数据。

**工程影响**

可能造成数据泄露、权限绕过、系统被攻击以及业务和合规风险。

#### 13. 开源许可证风险（License Compliance Risk）

**问题描述**

AI 生成的代码可能与受许可证约束的开源代码高度相似，且不提供来源；引入第三方依赖时，也可能没有检查许可证类型和商业使用限制。

**典型表现**

- 生成的代码片段与 GPL 等 Copyleft 代码高度相似，却无法追溯来源。
- 引入许可证不符合项目要求的依赖。
- 未识别第三方代码的许可证限制。
- 忽略依赖的来源和版本信息。
- 使用外部代码时没有保留必要的版权声明。

**工程影响**

可能引发知识产权争议、商业合规问题和后续依赖替换成本。

#### 14. 绕过测试（Test Bypassing）

**问题描述**

AI 在遇到测试失败时，在需求和预期行为没有变化的情况下，可能通过修改测试断言、删除测试用例或绕过测试逻辑来消除失败，而不是修复真实问题。

**典型表现**

- 在预期行为没有变化的情况下，为了通过测试而修改原有断言。
- 删除失败的测试用例。
- 跳过关键测试或降低测试要求。
- 修改测试数据以掩盖实际业务错误。

**工程影响**

使测试结果失去真实性，掩盖代码缺陷，导致质量门禁无法发挥应有作用。

#### 15. 测试覆盖不足（Insufficient Test Coverage）

**问题描述**

AI 生成测试时，可能只关注正常业务流程，没有充分覆盖异常路径、边界条件和跨模块业务约束。

**典型表现**

- 只覆盖正常输入和成功返回。
- 缺少异常、超时和失败场景测试。
- 忽略并发、幂等和重复请求场景。
- 没有覆盖跨系统数据一致性。
- 没有验证修改对其他模块的影响。

**工程影响**

测试无法充分暴露潜在缺陷，增加问题进入生产环境的概率。

#### 16. 验证结果不可信（Unreliable Verification）

**问题描述**

AI 对代码的验证过程不完整，或者没有真实执行构建、测试和运行检查，却给出已经验证通过的结论。

**典型表现**

- 没有执行测试，却声称测试通过。
- 只检查代码文本，没有实际编译。
- 只运行局部测试，没有执行必要的回归测试。
- 忽略测试失败和构建警告。
- 没有区分已验证结果与推测结果。

**工程影响**

使开发者无法准确判断代码质量，降低工程交付的可信度。

### 3.4 工程与协作流程问题

这一类问题关注 AI 是否能够遵循现有工程规范，安全地参与项目开发和协作。

#### 17. 改动范围失控（Uncontrolled Change Scope）

**问题描述**

AI 在完成局部需求时，可能修改超出任务范围的文件、模块或业务逻辑，没有有效控制变更边界。与 03 不同，这里的问题不在于没有理解依赖关系，而在于改动超出了任务边界。

**典型表现**

- 修改与当前需求无关的文件。
- 顺手重构大量现有代码。
- 格式化或批量重命名，导致 diff 中混入大量无关变更。
- 一次任务产生大量无法解释的代码变更。

**工程影响**

扩大代码审查和回归测试范围，增加引入新缺陷的概率。

#### 18. 依赖与环境问题（Dependency and Environment Issues）

**问题描述**

AI 生成代码时没有充分考虑项目实际运行环境、依赖关系和构建配置，导致代码无法在目标环境中正常运行。

**典型表现**

- 引入不兼容的依赖版本。
- 忽略 JDK、Node.js 等运行时版本要求。
- 修改构建配置后导致项目无法编译。
- 使用本地环境存在、生产环境缺失的配置。
- 忽略不同环境之间的配置差异。

**工程影响**

增加环境适配和部署成本，导致本地正常但测试或生产环境异常。

#### 19. 调试循环过长（Long Debugging Loop）

**问题描述**

AI 在面对错误时，可能缺少有效的根因分析能力，通过不断修改代码尝试解决问题，形成低效的调试循环。

**典型表现**

- 没有分析完整错误日志就直接修改代码。
- 同一个问题反复尝试不同实现。
- 修复表面报错，却没有解决根本原因。
- 新的修改不断引入新的错误。
- 缺少问题复现和验证过程。

**工程影响**

增加模型调用、人工介入和调试时间，降低整体开发效率。

#### 20. 技术债累积（Technical Debt Accumulation）

**问题描述**

AI 倾向于优先完成当前任务，可能留下临时实现、重复代码和职责混乱等问题，长期增加系统维护成本。重复实现本身见 09；本问题关注临时性实现长期未清理的累积效应。

**典型表现**

- 遗留无用代码、废弃分支和未清理的调试逻辑。
- 使用临时方案代替合理设计。
- 不断增加补丁，却没有清理历史问题。
- 模块职责逐渐混乱。
- 缺少必要的重构和文档更新。

**工程影响**

降低系统可维护性，增加后续需求开发、问题排查和架构演进成本。

#### 21. Git 操作风险（Version Control Risks）

**问题描述**

AI 在执行代码提交、分支管理、合并和回滚等操作时，可能没有正确识别当前工作区状态和已有变更。

**典型表现**

- 覆盖开发者尚未提交的代码。
- 错误执行回滚或重置操作。
- 将无关文件提交到当前分支。
- 未正确处理分支冲突。
- 在未确认变更范围时执行破坏性 Git 操作。

**工程影响**

可能造成代码丢失、版本混乱和协作冲突，严重时影响整个团队的开发进度。

### 3.5 效率与成本问题

这一类问题关注 AI Coding 是否真正提升开发效率，以及是否产生额外的时间和资源成本。

#### 22. Prompt 编写成本高（Prompt Engineering Overhead）

**问题描述**

开发者需要不断补充需求背景、项目约束、实现要求和验收标准，才能让 AI 正确理解任务，导致沟通和提示词编写成本增加。01 描述的是 AI 侧的信息丢失；本问题关注开发者为弥补信息缺失所付出的成本。

**典型表现**

- 同一需求需要多次补充说明。
- 项目规范和约束没有沉淀为可复用的说明文件，每次任务都要重新描述。
- 需要反复纠正 AI 的理解偏差。
- 提示词越来越长，维护难度越来越高。

**工程影响**

增加人机交互成本，削弱 AI Coding 在复杂任务中的效率优势。

#### 23. Token 成本高（Token Consumption）

**问题描述**

AI Coding 在持续开发过程中可能重复加载大量历史对话、项目文件和无关上下文，造成 Token 资源浪费。与 01 相反，本问题不是信息太少，而是上下文中无效信息太多。

**典型表现**

- 每轮对话都重复加载相同的规则和背景说明，即使与当前步骤无关。
- 加载与当前任务无关的文件。
- 上下文中存在大量重复信息。
- 为解决局部问题读取大量无关文件或整份大文件。

**工程影响**

增加模型调用成本，降低上下文利用效率，并可能挤占真正重要的信息空间。

#### 24. 生成等待与重试成本高（Generation and Retry Overhead）

**问题描述**

模型响应延迟、工具调用失败、网络异常和生成结果不符合预期等问题，会造成额外等待和重复执行。

**典型表现**

- 模型响应时间较长。
- 工具调用失败后需要重新执行。
- 生成结果不符合要求，需要多次重试。
- 多个开发任务之间存在不必要的等待。

**工程影响**

增加任务完成时间和资源消耗，影响开发流程的连续性。

#### 25. 生成速度与理解速度失衡（Generation-Understanding Gap）

**问题描述**

AI 生成代码的速度可能远高于开发者理解、审查和验证代码的速度，导致代码产出超过人工质量控制能力。

**典型表现**

- 一次生成大量代码，但开发者无法快速理解。
- 代码审查滞后于代码生成。
- 对 AI 生成的实现缺少充分验证。
- 开发者逐渐依赖 AI 解释自己没有充分理解的代码。

**工程影响**

增加隐藏缺陷和技术债的积累风险，使开发效率提升无法真正转化为交付质量提升。

### 3.6 团队与组织管理问题

这一类问题关注 AI Coding 在团队长期使用过程中，对人员能力、知识积累和组织管理产生的影响。

#### 26. 开发者技能退化（Developer Skill Degradation）

**问题描述**

开发者过度依赖 AI 进行需求分析、代码生成和问题排查，可能逐渐减少独立思考和解决问题的能力训练。

**典型表现**

- 遇到问题首先依赖 AI，而不是独立分析。
- 无法充分解释 AI 生成代码的实现原理。
- 对系统架构和底层技术的理解逐渐减弱。
- 缺少独立调试和定位问题的能力训练。

**工程影响**

降低团队技术自主性，增加对 AI 工具和模型服务的依赖。

#### 27. 知识难以沉淀（Knowledge Loss）

**问题描述**

AI 参与开发过程中形成的解决方案、技术决策和问题处理经验没有及时沉淀到项目知识库，导致工程经验难以复用。

**典型表现**

- 相同问题在不同任务中重复解决。
- 技术决策只保留在对话历史中。
- 缺少架构文档和关键实现说明。
- 代码变更没有同步更新相关文档。
- 新成员无法快速了解 AI 参与开发的历史决策。

**工程影响**

造成知识重复生产，增加团队协作和人员交接成本。

#### 28. 合规与审计困难（Compliance and Auditability）

**问题描述**

AI 参与代码生成和修改后，团队可能缺少完整的过程记录和审计机制，无法清晰追踪代码变更及其责任来源。

**典型表现**

- 无法确认哪些代码由 AI 生成或修改。
- 缺少关键操作和工具调用记录。
- 无法追踪模型输入中是否包含敏感数据。
- 缺少代码变更的审核和责任确认机制。
- 难以满足企业内部审计和合规要求。

**工程影响**

增加安全、合规和责任追溯风险，影响 AI Coding 在企业环境中的规模化应用。

#### 29. 效果难以评估（Difficulty in Measuring Effectiveness）

**问题描述**

团队缺少统一的评估标准，无法准确衡量 AI Coding 对开发效率、代码质量和软件交付能力的实际影响。

**典型表现**

- 只统计代码生成量，没有衡量代码质量。
- 只关注开发速度，没有考虑返工成本。
- 缺少 AI 生成代码的缺陷率统计。
- 无法比较使用 AI 前后的真实交付效率。
- 缺少团队级别的效果评估指标。

**工程影响**

难以判断 AI Coding 是否真正创造价值，也无法为工具选型和资源投入提供可靠依据。

### 3.7 系统运行与演进问题

这一类问题关注 AI 生成的代码进入真实运行环境后，是否能够满足系统可靠性、数据一致性和长期演进要求。

#### 30. 生产环境行为偏差（Production Behavior Gap）

**问题描述**

AI 生成的代码可能在局部测试或开发环境中表现正常，但进入真实生产环境后，受到流量、资源、外部依赖和运行环境等因素影响，出现非预期行为。

**典型表现**

- 本地运行正常，但生产环境出现异常。
- 高并发场景下出现资源竞争。
- 依赖服务的延迟、限流和配额限制在测试环境中没有体现。
- 真实数据规模下出现性能问题。
- 缺少必要的日志、指标和链路追踪。

**工程影响**

降低生产系统的稳定性，增加线上故障定位和恢复成本。

#### 31. 数据演进问题（Data Evolution Issues）

**问题描述**

AI 生成数据库变更和业务代码时，可能忽略历史数据兼容、Schema 演进、数据迁移以及新旧版本并存等问题。

**典型表现**

- 修改数据库字段时没有考虑历史数据。
- 数据结构变更与应用代码发布顺序不兼容。
- 忽略数据迁移过程中的失败和回滚。
- 新旧版本同时运行时出现数据兼容问题。
- 缺少大规模数据变更的性能和锁影响评估。

**工程影响**

可能导致数据丢失、数据不一致、发布失败以及系统无法平滑升级。

#### 32. 并发与分布式问题（Concurrency and Distributed System Issues）

**问题描述**

AI 在生成业务代码时，可能忽略多线程、分布式环境和跨系统交互中的一致性约束，导致局部正确的实现无法保证整体业务正确性。05 关注业务链路是否被完整识别；本问题关注在并发与分布式环境下如何正确实现。

**典型表现**

- 并发请求下出现重复执行和数据竞争。
- 消息重复消费或消息乱序没有正确处理。
- 缺少幂等性设计。
- 数据库与消息队列之间无法保证最终一致性。
- 分布式事务、补偿机制和状态协调设计不完整。

**工程影响**

可能造成重复扣款、库存超卖、订单状态不一致和跨系统数据异常等严重业务问题。

#### 33. 故障恢复机制缺失（Failure Recovery Gaps）

**问题描述**

AI 生成代码时可能只关注正常执行流程，没有充分考虑系统发生异常后的恢复能力和业务补偿机制。与 11 不同，本问题关注故障发生后系统和业务能否恢复到正确状态。

**典型表现**

- 部分操作成功、部分失败后（如扣款成功但下单失败），缺少对账或回滚机制。
- 任务中断后无法从断点恢复，只能整体重跑。
- 缺少熔断、降级和限流机制。
- 跨系统操作失败后没有补偿流程。
- 系统恢复后无法识别和处理未完成任务。

**工程影响**

增加故障扩散和业务数据不一致的风险，降低系统的可恢复性。

## 4. 后续工程治理方向

上述问题覆盖了 AI Coding 从需求理解、代码生成、质量验证到生产运行的多个阶段。这些问题并不是相互独立的：上下文丢失可能导致需求理解偏差，进而造成代码实现错误，最终表现为测试失败或生产环境故障。

后续治理需要围绕完整的软件工程链路建立约束和验证机制，而不是只针对单个问题进行修补。

| 治理方向 | 重点关注 |
| --- | --- |
| Context Engineering | 上下文组织、检索、压缩和持续管理 |
| Requirement Engineering | 需求澄清、业务规则提取和影响范围分析 |
| Architecture Constraints | 架构边界、模块职责和依赖约束 |
| Code Quality Gate | 静态检查、代码审查和规范校验 |
| Testing & Evaluation | 测试策略、自动化评测和验证可信度 |
| Security & Compliance | 安全扫描、依赖治理和审计 |
| Workflow Engineering | 任务拆分、工具调用和交付流程 |
| Runtime Reliability | 可观测性、数据一致性和故障恢复 |

## 5. 文档定位与演进规划

本文定位为 AI Coding Engineering 的问题定义文档，重点是识别问题、统一概念和建立分类，不在当前阶段提前展开具体解决方案。

后续按照以下路径持续演进：

1. **问题识别**：整理真实工程中的典型问题。
2. **问题分析**：分析问题产生的技术原因和工程原因。
3. **治理设计**：提出对应的架构约束、流程和技术机制。
4. **工程实践**：结合真实项目验证治理方案。
5. **持续评估**：建立质量、效率和可靠性的评估指标。

最终目标不是让 AI 生成更多代码，而是建立一套能够约束、验证和持续改进 AI Coding 的工程体系。
