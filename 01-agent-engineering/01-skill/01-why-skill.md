# Agent Skill 实战：从 Prompt 膨胀到可维护的能力模块

> Skill 的价值不是把 Prompt 换个文件存起来，而是把反复出现的流程知识、领域规则和执行方法，组织成可发现、可复用、可评测、可维护的能力单元。
>
> **规范与时效说明：** 本文涉及的 Agent Skills 文件格式以 [Agent Skills 开放规范](https://agentskills.io/specification) 为准；平台的发现、加载、脚本执行和权限行为，以各平台当前文档为准。本文核对时间：2026 年 11 月。

## 1. TL;DR

| 问题 | 结论 |
|---|---|
| 为什么需要 | 将局部任务规则从全局 Prompt 中拆出，降低规则耦合，让能力可以独立演进 |
| 什么时候引入 | 存在值得独立管理的稳定流程知识、领域规则或团队规范 |
| 什么时候不引入 | 一次性任务、持续变化的流程，或问题本质是动态知识检索、外部系统连接、独立并行执行 |
| 主要成本 | 路由误差、上下文与执行开销、维护评测成本，以及指令和脚本带来的安全风险 |
| 核心原则 | 先观察真实任务和失败，再决定是否抽象；不要为了模块化而模块化 |

---

## 2. 问题从哪里来：系统提示词开始失控

Agent 初期通常直接通过 System Prompt 描述角色、任务、工具使用方式和输出约束。场景少时，这种方式简单有效；场景增加后，局部流程、领域知识、全局规则和工具说明会不断堆积。

问题不只是 Prompt 变长，而是职责边界逐渐模糊：

1. **规则耦合：** 修改某个业务场景的规则，可能影响其他任务。
2. **上下文污染：** 当前任务用不到的规则仍可能占据上下文。
3. **知识重复：** 相似流程散落在不同提示词和会话中，难以统一维护。
4. **验证困难：** 很难独立判断某条能力规则是否有效，也难以定位失败来自规则、模型还是工具执行。

Prompt 变长不必然导致效果下降。真正需要治理的是规则的适用范围、优先级、复用方式和验证边界。

## 3. Skill 是什么：开放格式与能力组织方式

Skill 可以理解为：**围绕一类任务组织起来的一组指令、领域知识和可选执行资源，让 Agent 在适当场景下复用相对稳定的做法。**

它不只是 Markdown 提示词，也可以包含参考资料、模板和脚本：

```text
pdf-processing/
├── SKILL.md              # 必需：入口、用途、流程和边界
├── references/           # 可选：按需读取的参考资料
├── scripts/              # 可选：可执行脚本
└── assets/               # 可选：模板、图片等静态资源
```

### 3.1 文件格式已经有开放规范

Agent Skills 已经不是完全由各个平台自行定义的格式。开放规范定义了基本目录结构和元数据：

- `SKILL.md` 是必需文件，包含 YAML frontmatter 和 Markdown 指令正文。
- `scripts/`、`references/`、`assets/` 是可选目录。
- `name` 最长 64 个字符，使用小写字母、数字和连字符，并受目录名匹配等规则约束。
- `description` 最长 1024 个字符，用于说明能力和适用场景。
- 规范建议将 `SKILL.md` 主体控制在约 500 行、5000 tokens 以内；这是可维护性建议，不应误读为所有平台的硬性运行限制。
- 参考资料尽量从 `SKILL.md` 直接链接，避免多层引用链条，降低模型遗漏关键内容的概率。

因此，需要区分两个层面：

| 层面 | 统一程度 | 需要关注的差异 |
|---|---|---|
| 文件格式与元数据 | 有开放规范 | 目录、字段、命名和描述约束 |
| 平台运行行为 | 不能仅凭文件格式推断 | Skill 如何发现和加载、脚本运行时、工具集成、权限控制 |

换句话说，**文件格式可移植，不代表运行行为和安全能力完全一致。** 把同一份 Skill 放到不同 Agent 平台前，仍然需要检查各平台的兼容性说明和运行限制。

### 3.2 渐进式披露：按需加载，而不是一次塞满

在支持渐进式披露的平台中，Skill 内容可以分层进入上下文。以文件式 Skill 的常见设计理解：

| 层次 | 内容 | 典型时机 | 目的 |
|---|---|---|---|
| 元数据 | 名称、描述 | 发现可用 Skill 时 | 判断能力是否相关 |
| 核心指令 | `SKILL.md` 正文 | Skill 被选中后 | 提供任务流程和约束 |
| 扩展资源 | references、脚本、assets | 任务需要时 | 避免低频细节提前占用上下文 |

这是对渐进式加载机制的概括，不意味着所有平台采用完全相同的实现。脚本源代码通常不需要全文进入模型上下文，但执行结果、错误信息和读取的文件内容仍可能占用上下文。

**渐进式披露解决“何时加载什么内容”；Skill 解决“如何组织一类任务能力”。** 两者相关，但不是同一个概念。

### 3.3 Skill、System Prompt、MCP、RAG、Subagent 的边界

| 机制 | 主要职责 | 更适合解决的问题 |
|---|---|---|
| System Prompt | 全局身份、行为约束和通用规则 | 所有任务都必须遵守的底线 |
| Skill | 稳定流程知识、领域规则和执行方法 | 值得独立维护和复用的任务能力 |
| MCP / Tool | 通过接口向 Agent 暴露工具、数据和外部系统能力 | 查询数据库、调用 API、读写外部系统 |
| RAG | 从外部知识源检索相关内容 | 大规模、动态或持续更新的事实与文档 |
| Subagent | 在独立上下文中委派子任务 | 上下文隔离、复杂任务拆分和并行执行 |
| Memory | 保存跨会话或跨任务需要保留的信息 | 用户偏好、历史状态和长期上下文 |

需要修正一种过度简化的说法：“MCP 给手，Skill 教怎么用”。更准确地说：

> **MCP 通过标准化协议向 Agent 暴露工具、数据和外部系统能力；Skill 组织完成特定任务所需的流程知识、领域规则和执行方法，也可以附带本地脚本。**

Skill 本身可能包含可执行脚本，因此它并非只有“说明书”这一面；MCP 与 Skill 也不是互斥关系。

## 4. 什么时候应该引入 Skill

不要只问“任务是否重复”。个人任务可能不重复，但团队可能需要共享；真正的判断起点应该是：

**是否存在值得独立管理的能力或知识？**

可以按问题性质选择机制：

```text
是否存在值得独立管理的能力或知识？
├── 否 → 先用当次 Prompt
└── 是
    ├── 主要是动态事实或文档检索 → RAG
    ├── 主要是连接外部系统 → MCP / Tool
    ├── 需要独立上下文或并行执行 → Subagent
    ├── 所有任务都适用的全局约束 → System Prompt
    └── 稳定流程知识、领域规则或团队规范 → Skill
```

这些机制可以组合。例如，Skill 描述数据分析流程，RAG 检索最新指标定义，MCP 查询数据仓库，Subagent 并行分析不同业务分区。

适合考虑 Skill 的信号包括：

- 团队反复解释同一套流程或规范；
- 任务包含稳定的多步流程和明确验收条件；
- 存在模型容易忽略的领域知识、内部约定或边界规则；
- 专家经验需要被团队成员或多个 Agent 复用；
- 某些确定性步骤需要脚本固定实现。

如果流程仍在频繁变化，先用 Prompt 验证；等真实用例和边界稳定后再抽象。

## 5. 引入 Skill 的主要成本与风险

### 5.1 上下文成本：数量增加也有代价

如果平台会把可用 Skill 的描述放进模型上下文，那么 Skill 数量增加会带来元数据开销。开放规范给出的粗略参考是每个 Skill 的元数据约 100 tokens，因此可以用下面的方式估算：

```text
C_discovery ≈ N × 100 tokens
50 个 Skill ≈ 5,000 tokens
```

这只是渐进式披露场景下的粗略预算，不代表所有平台都会以相同方式常驻加载，也不等于每个 Skill 的真实 Token 数都固定为 100。第三方对 Anthropic 官方仓库 Skill 的测量也显示元数据大小存在差异；具体数据应以测量方法和样本范围为准。

此外还要考虑正文加载、参考资料读取、工具调用轮次和端到端延迟。不能只比较 Skill 元数据与完整 System Prompt 的 Token 数，而忽略内容是否相同、何时加载以及实际进入上下文的比例。

### 5.2 路由和执行可靠性成本

- **漏触发：** 用户需要某项能力，但模型没有选中对应 Skill。
- **误触发：** 不相关任务加载了专用 Skill。
- **执行不完整：** Skill 已加载，但模型没有完成关键步骤。
- **职责冲突：** 多个 Skill 描述重叠，模型难以判断优先使用哪个。
- **运行环境差异：** 文件格式相同，不代表脚本依赖、网络、文件权限和工具集成相同。

### 5.3 安全风险不只是脚本执行

Skill 同时包含模型会读取的指令和可能被执行的资源，至少要关注：

1. **指令注入：** `SKILL.md` 或 references 中可能包含诱导模型泄露信息、忽略上层约束或执行越权操作的内容。
2. **恶意路由描述：** description 可能通过宽泛或误导性措辞诱导错误触发，或抢占其他 Skill 的适用场景。
3. **脚本与依赖风险：** 脚本可能读写文件、访问网络、执行命令或引入不可信依赖。
4. **权限误判：** 某些平台支持类似 `allowed-tools` 的字段，但规范中相关字段标注为 Experimental，不能把它当作跨平台统一的安全边界。

治理建议：

- 将第三方 Skill 视为不可信输入，审查 `SKILL.md`、references、脚本和依赖；
- 检查 description 是否存在过宽或误导性的触发描述；
- 使用最小权限和隔离运行环境，不在 Skill 中硬编码密钥；
- 对删除、覆盖、外发数据等敏感操作设置明确确认和校验机制；
- 用负样本测试误触发，用权限测试验证脚本实际能访问什么。

## 6. 一个最小对照实验：验证 Skill 是否真的有价值

“真实失败案例决定 Skill 内容”是一个工程主张，不能只靠经验描述。更可靠的方式是建立对照实验，而不是先写一份很长的 Skill，再凭感觉判断效果。

### 6.1 实验设计

先选择一个边界清晰的任务，例如 PDF 表格提取。准备 10 个任务样例：

- 5 个应该触发 Skill 的正样本；
- 5 个不应该触发 Skill 的负样本。

每个任务分别运行两组：

- **Without Skill：** 不提供该 Skill；
- **With Skill：** 提供 Skill，并允许 Agent 按平台机制发现和加载。

为了减少随机性，每个任务重复运行 3 次。固定模型版本、工具集合、输入文件、运行环境和其他配置；如果平台无法固定某些变量，需要在实验记录中说明。

### 6.2 记录指标

| 指标 | 说明 |
|---|---|
| 触发召回率 | 应触发的任务中，正确触发的比例 |
| 误触发率 | 不应触发的任务中，错误触发的比例 |
| 关键步骤完成率 | 预先定义的必要步骤实际完成比例 |
| 任务成功率 | 最终产物是否通过客观验收 |
| Token 消耗 | 输入、输出及可获得的上下文消耗 |
| 工具调用轮次 | 完成任务所需的工具调用次数 |
| 端到端耗时 | 从任务开始到结果完成的时间 |

实验记录模板：

| Task ID | 应触发 | Without Skill 结果 | With Skill 结果 | 关键步骤 | Token | 工具轮次 | 耗时 |
|---|---|---|---|---|---:|---:|---:|
| T01 | 是 | 待实测 | 待实测 | 待实测 | — | — | — |
| T02 | 是 | 待实测 | 待实测 | 待实测 | — | — | — |
| T03 | 是 | 待实测 | 待实测 | 待实测 | — | — | — |
| T04 | 是 | 待实测 | 待实测 | 待实测 | — | — | — |
| T05 | 是 | 待实测 | 待实测 | 待实测 | — | — | — |
| T06 | 否 | 待实测 | 待实测 | 不应误触发 | — | — | — |
| T07 | 否 | 待实测 | 待实测 | 不应误触发 | — | — | — |

**当前这里给出的是实验方案，不是实验结果。** 在实际运行并记录数据前，不应声称 Skill 已经提高成功率、降低 Token 或减少工具调用。

### 6.3 如何解释结果

- 触发召回率提高，但误触发率也明显提高：description 可能过宽，需要重新定义边界。
- 触发正常，但关键步骤完成率没有改善：问题可能在正文流程、验收标准或模型遵循能力。
- 成功率提高，但 Token 和耗时明显增加：需要判断收益是否值得额外成本。
- 只有个别样例改善：样本可能不足，或 Skill 只对特定子场景有效。
- With Skill 结果更差：检查 Skill 是否引入了冲突、过度约束或错误工具路径。

评测的目的不是证明 Skill 一定有用，而是判断它在什么任务范围内有用、付出了什么成本，以及是否值得继续维护。

## 7. 常见问题诊断表

| 症状 | 可能原因 | 优先处理方式 |
|---|---|---|
| 相关任务不触发 | description 不清晰、触发条件缺失 | 补充真实用户表达，建立正样本 |
| 无关任务误触发 | 描述过宽、职责边界重叠 | 收窄范围，增加负样本 |
| 触发后仍漏步骤 | 主流程不清、验收条件不明确 | 明确关键步骤、停止条件和检查项 |
| 参考信息没有被读取 | 引用层级过深、导航不清晰 | 从主文件直接链接关键资料 |
| 脚本在目标环境失败 | 依赖、路径、权限或网络假设错误 | 在目标运行环境验证依赖与权限 |
| 改完一个场景，其他场景退化 | 缺少回归评测、Skill 职责冲突 | 固定回归集，比较修改前后结果 |

## 8. 经验总结

1. **Skill 是能力治理方式，不是 Prompt 的新包装。** 先找到值得独立管理的知识和流程。
2. **开放文件规范不等于运行行为完全统一。** 文件格式、加载策略、执行环境和权限需要分别验证。
3. **渐进式披露有上下文收益，也有路由和读取成本。** Skill 越多，不代表 Agent 越强。
4. **Skill 可以包含脚本。** MCP/Tool 提供外部系统能力，Skill 组织任务方法，两者可以协同。
5. **安全审查覆盖指令、元数据、引用资料和脚本。** 不要把 Skill 当成普通文档。
6. **评测结果比文档完整度更重要。** 没有对照实验，就不要把预期收益写成已验证结论。
