# 为什么需要 Skill：从系统提示词失控到能力模块化

> 本文讨论的不是某个 Agent 框架的具体配置，而是一个工程问题：当 Agent 需要承担越来越多任务时，如何组织它的指令、知识和执行流程，让能力可以复用、按需加载，并且能够持续维护。

## 1. 问题从哪里来：系统提示词开始失控

在最初的 Agent 实践中，最直接的做法通常是把行为规则写进 System Prompt：

- 你是什么角色；
- 你需要完成哪些任务；
- 遇到不同场景应该遵循什么流程；
- 哪些情况需要调用工具；
- 输出必须满足什么格式。

任务少的时候，这种方式简单、直接，也容易理解。

但随着业务场景增加，问题开始出现。

### 1.1 指令不断累积

每增加一种任务，就在系统提示词里追加一段规则。时间久了，提示词逐渐变成一份混合文档：既有全局行为约束，也有某个业务场景的操作步骤，还有大量例外条件。

这会带来两个问题：

1. **全局规则和局部规则混在一起。** 修改一个局部场景，可能需要检查整份提示词，避免影响其他任务。
2. **上下文里存在大量当前任务用不到的信息。** Agent 每次执行任务，都可能携带与本次任务无关的指令和背景。

这里需要注意：提示词变长并不必然导致模型表现下降。真正的问题是指令之间的相关性、优先级和边界越来越难管理，有限的上下文预算也更难分配。

### 1.2 相似能力难以复用

假设一个 Agent 同时负责：

- 查询项目代码并解释调用链；
- 根据技术规范生成接口文档；
- 分析线上故障并整理排查步骤；
- 按团队规范编写技术方案。

如果每种任务的完整流程都写在 System Prompt 中，那么能力复用往往依赖复制粘贴。不同任务中的相似规则可能逐渐出现多个版本，后续维护容易产生不一致。

### 1.3 修改和验证缺少清晰边界

当所有规则集中在一份提示词中时，很难回答几个工程问题：

- 某个任务的规则应该由谁维护？
- 修改这段指令会影响哪些任务？
- 如何单独验证某项能力？
- 某项能力不再需要时，应该删除哪部分内容？

这说明问题已经不只是“提示词写得够不够好”，而是 Agent 能力缺少合理的组织边界。

## 2. Skill 是什么：把特定任务的做法组织成可复用能力

可以先把 Skill 理解为：

**围绕一类明确任务组织起来的一组指令、知识和可选执行资源，使 Agent 在满足触发条件时，能够按照相对稳定的流程完成任务。**

它不是简单地把一段 Prompt 移到另一个 Markdown 文件里。真正有价值的地方，是让某项能力具备相对独立的边界和维护方式。

一个 Skill 通常可以包含以下内容：

| 组成部分 | 作用 | 示例 |
| --- | --- | --- |
| 元信息与描述 | 说明能力是什么、适用于什么任务 | 名称、用途、触发条件 |
| 指令与流程 | 约束任务如何执行 | 分析步骤、决策规则 |
| 领域知识 | 提供完成任务所需的背景 | 术语、规范、业务约束 |
| 参考资料 | 在需要时提供更详细的信息 | API 说明、设计规范 |
| 脚本或工具说明 | 支持确定性操作或外部交互 | 校验脚本、命令使用说明 |
| 输出与验证要求 | 定义结果应该是什么样，以及如何检查 | 输出结构、检查清单 |

不同 Agent 平台对 Skill 的文件格式、加载机制和执行能力可能有不同约定。上表描述的是一种能力组织思路，不代表所有平台都必须采用相同目录结构或文件规范。

### 2.1 Skill 与 System Prompt 的边界

两者并不是替代关系，更合理的方式是按职责分工：

- **System Prompt：** 放置跨任务都成立的基础身份、全局行为约束和最高优先级规则。
- **Skill：** 放置某一类任务专属的知识、流程、约束和交付标准。

例如，“不要编造不存在的事实”可能是全局规则；“排查 Java 服务的线程池问题时，先确认队列类型、拒绝策略和监控指标”则更适合放在对应的排障 Skill 中。

判断依据不是规则长短，而是它是否跨任务通用。

### 2.2 Skill 与 Tool 的边界

Skill 和 Tool 解决的不是同一个问题：

- **Tool 负责执行操作。** 例如查询数据库、读取文件、调用 HTTP API。
- **Skill 负责组织完成任务的方法。** 例如说明何时查询数据库、查询哪些字段、如何解释结果，以及失败时如何处理。

Skill 可以指导 Agent 使用一个或多个 Tool，但 Skill 本身不等于 Tool，也不意味着其中的指令天然拥有执行外部操作的能力。

可以用一句话区分：

> Tool 提供“能做什么”，Skill 组织“面对某类任务应该怎么做”。

## 3. Skill 带来的变化，以及它没有解决的问题

把能力从一份大提示词中拆出来，可能带来几个收益：

1. **职责更清晰：** 全局约束与任务专属流程分开维护。
2. **能力更容易复用：** 多个任务可以复用同一套经过验证的流程和资料。
3. **变更范围更容易控制：** 可以围绕单项能力进行评审、测试和迭代。
4. **上下文组织更灵活：** 在支持按需加载的平台中，可以只在相关任务发生时加载对应能力。

但这并不意味着引入 Skill 就自动解决了 Agent 的工程问题。

### 3.1 Skill 可能带来的新成本

| 新问题 | 具体表现 | 应对思路 |
| --- | --- | --- |
| 能力拆分过细 | 一个任务需要连续加载多个零散 Skill | 按完整任务边界组织能力，避免为了拆分而拆分 |
| 触发不准确 | 应该使用时没有命中，或无关任务误触发 | 写清适用场景、输入特征和排除条件 |
| 规则重复 | System Prompt 与多个 Skill 中存在冲突规则 | 明确规则归属，减少重复定义 |
| 版本不一致 | 参考文档或脚本更新后，Skill 仍使用旧规则 | 建立版本管理和定期校验机制 |
| 结果不稳定 | 同一 Skill 在不同输入下产生不同结果 | 提供示例、边界条件和可验证的输出标准 |

Skill 只是让能力有了更好的组织单元，并不会自动保证模型遵循指令，也不能替代测试、权限控制、工具治理和运行时监控。

## 4. 什么时候应该使用 Skill

不是所有 Prompt 都值得封装成 Skill。可以从任务是否具有复用价值和流程稳定性来判断。

**适合封装为 Skill 的情况：**

- 某类任务会反复出现；
- 任务有相对稳定的步骤或判断规则；
- 需要组合多份领域知识、参考资料或工具；
- 输出有明确的质量标准；
- 这项能力需要独立维护和持续改进。

例如，团队反复进行代码评审，而且评审维度、输出结构和检查步骤相对稳定，就可以考虑封装为代码评审 Skill。

**不适合封装为 Skill 的情况：**

- 只是一次性的简单问题；
- 规则对所有任务都适用，应放在全局指令中；
- 需求本质上是执行一个外部操作，应由 Tool 提供能力；
- 内容属于跨任务的用户偏好或历史状态，更适合由 Memory 等机制管理；
- 流程极其简单，封装和路由成本已经超过复用收益。

一个实用的判断方式是：

> 如果这套做法会被重复使用，并且值得独立维护、测试和演进，那么它才有成为 Skill 的价值。

## 5. 如何设计一个可维护的 Skill

设计时，建议先定义任务边界，再组织文件和指令。不要一开始就追求复杂目录结构。

### 5.1 先明确任务边界

至少回答四个问题：

1. **目标：** 这个 Skill 要解决什么问题？
2. **触发：** 什么输入或任务场景应该使用它？
3. **输入：** 执行任务需要哪些信息？缺少信息时如何处理？
4. **交付：** 最终应该输出什么，如何判断结果合格？

如果这四个问题都无法说清楚，通常说明任务边界还不够明确。

### 5.2 指令围绕任务流程组织

一个相对清晰的流程可以包含：

1. 识别任务和确认输入；
2. 检查前置条件与约束；
3. 按步骤执行；
4. 处理异常、缺失信息和不确定结果；
5. 按约定格式交付；
6. 执行必要的结果校验。

不要只写“请认真分析并给出最佳答案”这类抽象要求。应尽可能把关键判断条件、禁止事项和验收标准写清楚。

### 5.3 把详细资料与主流程分开

当 Skill 需要较多领域知识时，可以将核心流程与参考资料分离：

- 主指令保留任务目标、关键步骤和资料索引；
- 详细规范放在独立参考文件中；
- 确定性、可重复的操作尽可能由脚本或工具完成。

在支持渐进式加载的平台中，Agent 可以先读取能力描述，再按任务需要加载详细指令或参考资料。这种方式通常称为 Progressive Disclosure（渐进式披露/按需加载）。

需要区分的是：**Skill 是能力组织单元，Progressive Disclosure 是上下文加载策略。** Skill 可以配合按需加载，但二者不是同一个概念，也不是所有平台都会自动提供相同的加载机制。

### 5.4 给 Skill 配置可验证的验收标准

例如，一个代码评审 Skill 不应该只要求“检查代码质量”，还可以明确：

- 是否识别了潜在的空指针、并发和资源释放问题；
- 是否说明问题出现的前置条件；
- 是否评估了影响范围；
- 是否给出可执行的修改建议；
- 是否区分确定的问题与需要进一步验证的风险。

验收标准越具体，越容易通过测试样例发现 Skill 的缺陷。

## 6. 从一次封装到持续维护

Skill 不应该被当作写完就不再变化的静态 Prompt。更合理的是把它纳入常规工程迭代。

可以采用一个轻量闭环：

```text
发现重复任务
    ↓
抽象任务边界
    ↓
编写 Skill
    ↓
使用真实样例验证
    ↓
记录失败与边界案例
    ↓
修订指令、资料或工具
    └──────────→ 持续迭代
```

每次迭代时，可以重点检查：

- 触发条件是否准确；
- 是否存在重复或冲突规则；
- 参考资料是否过期；
- 失败案例是否已经覆盖；
- 修改是否影响其他任务；
- 是否有代表性样例可以回归验证。

这里有一个重要原则：**不要只根据一次成功输出判断 Skill 是否有效。** 至少应该准备正常输入、边界输入和异常输入，观察它在不同情况下是否仍能遵守预期流程。

## 7. 总结：从 Prompt 管理走向 Agent 能力工程化

Skill 的价值不在于把长 Prompt 拆成多个文件，而在于让 Agent 的某类任务能力具备清晰的边界、可复用的知识与流程，以及独立验证和持续维护的可能。

但 Skill 不是 Agent 工程化的全部：

- System Prompt 管理全局约束；
- Tool 提供外部执行能力；
- Skill 组织特定任务的方法；
- Progressive Disclosure 决定上下文如何按需加载；
- Memory 管理跨任务需要保留的状态或历史信息。

这些机制各自解决不同层面的问题，需要根据系统实际需求组合，而不是把所有能力都塞进 Skill。

**当 Agent 的任务开始重复、规则开始膨胀、能力开始难以维护时，就应该从单纯编写 Prompt 转向设计可复用、可验证、可演进的能力单元。**

- [ ] Skill 的任务边界和触发条件是否明确？
- [ ] 全局规则、任务规则和工具执行职责是否分开？
- [ ] 是否避免把 Skill 与 Tool、Memory、Progressive Disclosure 混为一谈？
- [ ] 是否写明输入要求、异常处理和输出验收标准？
- [ ] 是否用真实样例验证，而不只依赖主观判断？
- [ ] 是否确认参考资料和脚本与当前版本一致？
