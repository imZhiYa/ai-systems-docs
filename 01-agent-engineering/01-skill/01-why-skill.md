# Agent Skill 实战：从 Prompt 膨胀到可维护的能力模块

> Skill 不是把一段 Prompt 换个文件存起来。它真正解决的是：当 Agent 要处理越来越多重复任务时，如何把流程、领域知识和执行资源拆成边界清晰、按需使用、能够评测和维护的能力单元。
>
> 本文以 Anthropic Agent Skills 的文件式 Skill 作为具体例子。涉及目录格式、元数据和加载行为的部分属于平台实现；任务边界、按需加载、评测和安全治理则是更通用的工程设计思路。

## 1. TL;DR

| 问题 | 结论 |
|---|---|
| 为什么需要 | 把重复出现的流程性知识从全局 Prompt 中拆出来，减少无关上下文，让能力可以独立复用和维护 |
| 什么时候引入 | 任务重复、流程相对稳定、存在领域规范或明确验收标准，并且值得单独维护 |
| 什么时候不引入 | 一次性任务、需求仍在频繁变化、通用规则，或本质上只是调用外部系统 |
| 最大成本 | 触发不确定、上下文与工具调用开销、维护和评测成本，以及脚本执行带来的安全风险 |
| 怎么写 | 先找真实失败点，再定义触发条件和任务边界；主流程保持精简，资料按需拆分，确定性操作交给代码 |
| 最容易踩的坑 | Skill 不触发或误触发、正文过长、引用层级过深、把模型该判断的事和脚本该执行的事混在一起 |

---

## 2. 问题从哪里来：系统提示词开始失控

最初做 Agent，最直接的方式通常是把规则写进 System Prompt：

- 你是什么角色；
- 你要处理哪些任务；
- 遇到不同场景应该执行什么流程；
- 什么情况下调用工具；
- 输出必须满足什么格式。

任务少的时候，这种方式简单有效。但当业务场景逐渐增加，Prompt 会慢慢变成一份混合文档：全局行为约束、局部业务流程、领域知识、工具使用说明和异常处理规则全都堆在一起。

我认为这里真正值得关注的，不是 Prompt 到了多少 token，而是它开始出现几个工程问题。

### 2.1 全局规则和局部规则混在一起

比如一个 Agent 同时负责代码评审、数据分析、技术文档生成和故障排查。每增加一种场景，就往 System Prompt 里追加一段规则。

时间久了：

1. 修改某个场景，需要担心是否影响其他任务；
2. 大量当前任务用不到的规则仍然留在上下文中；
3. 相似规则散落在不同位置，逐渐出现多个版本；
4. 很难判断某条规则究竟属于全局约束，还是某个任务的局部要求。

Prompt 变长不必然意味着效果下降。更本质的问题是：规则的职责、优先级和适用范围越来越难治理。

### 2.2 重复解释，经验无法沉淀

同一套代码规范、报告格式、数据口径，可能在不同会话里反复解释。团队成员也可能各自维护一份相似的 Prompt。

这类知识没有稳定的归属位置，也缺少统一的变更记录。换会话、换 Agent，甚至换一个维护者，都可能重新踩一遍之前的问题。

### 2.3 能力缺少独立验证边界

当所有规则集中在一个大 Prompt 中，很难单独回答：

- 代码评审规则改动后，应该回归哪些任务？
- 某个流程为什么没有执行，是规则没写清楚，还是模型没有遵循？
- 某项能力不再需要时，应该删除哪部分内容？
- 新增一条业务规范，会不会破坏其他任务？

这已经不是单纯的 Prompt 编写问题，而是 Agent 能力的组织和治理问题。

## 3. Skill 是什么：流程知识 + 可选执行资源

以文件式 Agent Skill 为例，可以把 Skill 理解为：

**围绕一类明确任务组织起来的一组指令、领域知识和可选资源，让 Agent 在合适的任务场景下复用一套相对稳定的做法。**

它通常不只是一个 Markdown 文件，还可以包含参考资料、模板和脚本。例如：

```text
pdf-processing/
├── SKILL.md              # 入口：用途、触发条件、核心流程
├── references/
│   ├── forms.md          # 表单处理细节
│   └── pdf-layout.md     # PDF 版式说明
├── scripts/
│   ├── extract_tables.py # 确定性提取
│   └── validate.py       # 输出校验
└── assets/
    └── report-template.xlsx
```

这里的目录只是组织示例，不是所有平台都必须遵循的统一规范。具体文件约定、脚本运行方式和加载行为，需要以目标 Agent 平台为准。

### 3.1 核心机制：渐进式披露（Progressive Disclosure）

在支持渐进式加载的平台中，Skill 不需要一开始就把所有内容塞进上下文。以 Anthropic Agent Skills 的文件式机制为例，可以用三个层次理解：

| 层次 | 内容 | 典型加载时机 | 工程目的 |
|---|---|---|---|
| L1：元数据 | 名称、描述等 | Agent 发现可用 Skill 时 | 让模型判断某项能力是否相关 |
| L2：核心指令 | `SKILL.md` 正文 | Skill 被选中或触发后 | 提供执行流程和关键约束 |
| L3：扩展资源 | 参考文档、模板、脚本 | 任务需要时 | 避免低频细节占用常驻上下文 |

需要注意两个边界：

- 这是对特定文件式 Skill 加载模式的概括，不代表所有框架都采用完全相同的 L1/L2/L3 实现。
- 脚本源代码通常不需要作为指令全文放进模型上下文，但脚本执行仍然需要运行环境；执行结果、错误信息或文件内容仍可能进入上下文。

**渐进式披露解决的是“什么时候把什么内容放进上下文”，Skill 解决的是“如何组织一类任务能力”。两者相关，但不是同一个概念。**

### 3.2 Skill、System Prompt、MCP、RAG 和 Subagent 怎么区分

| 机制 | 主要职责 | 更适合解决的问题 |
|---|---|---|
| System Prompt | 全局身份、行为约束和通用规则 | 所有任务都需要遵守的底线 |
| Skill | 特定任务的流程、规范和经验 | 重复出现、值得沉淀的任务方法 |
| MCP / Tool | 向 Agent 暴露外部能力或系统接口 | 查询数据库、调用 API、读写外部系统 |
| RAG | 检索外部事实和文档内容 | 大规模知识库、动态事实查询 |
| Subagent | 将子任务交给独立执行上下文 | 复杂任务拆分、上下文隔离、并行执行 |
| Memory | 保存跨会话或跨任务需要保留的信息 | 用户偏好、历史状态、长期上下文 |

一句话区分 Skill 和 MCP：

> **MCP 给 Agent 提供“手”，Skill 告诉 Agent 面对某类任务应该如何使用这些能力。**

例如，MCP 提供查询数据仓库的接口；Skill 说明应该查询哪些指标、遵循什么统计口径、如何处理异常值，以及最终报告如何组织。二者通常是组合关系，不是互斥选择。

## 4. 什么时候该引入 Skill

不要为了使用 Skill 而使用 Skill。一个任务是否值得封装，至少要看它是否重复、流程是否稳定，以及是否值得独立维护。

### 4.1 适合引入的信号

- 同一段流程或规范已经被重复解释多次；
- 任务包含明确的多步流程，例如读取、校验、转换、输出；
- 输出格式有严格要求，例如报告模板、代码规范或固定字段；
- 存在模型容易忽略的领域知识，例如内部 API、业务口径和团队约定；
- 某些步骤需要脚本保证确定性，例如解析、校验、计算和批量转换；
- 团队希望把专家经验沉淀下来，让不同 Agent 或成员复用。

### 4.2 不建议引入的情况

- 一次性任务，后续几乎不会复用；
- 需求还不稳定，规则每天都在变化；
- 模型本身已经能稳定完成的简单通用任务；
- 本质是大规模事实查询，更适合 RAG；
- 本质只是连接外部系统，更需要 Tool 或 MCP；
- 任务需要强隔离、独立上下文或并行执行，更适合 Subagent；
- 封装、路由和维护成本已经超过复用收益。

### 4.3 一个简单的判断流程

```text
这个任务是否会重复出现？
├── 否：直接使用当次 Prompt
└── 是
    ├── 主要需求是连接外部系统？── 是：Tool / MCP
    └── 否
        ├── 规则是否所有任务都适用？── 是：System Prompt
        └── 否：流程是否稳定且值得复用？
                ├── 否：继续用 Prompt 验证
                └── 是：考虑封装为 Skill
```

我的经验原则是：**先用 Prompt 把任务跑通，观察重复出现的模式；等流程相对稳定，再把真正值得复用的部分沉淀为 Skill。**

## 5. 引入 Skill 的代价

Skill 并不是免费的抽象。它降低了一部分 Prompt 管理成本，同时引入了新的运行和治理成本。

### 5.1 上下文与性能成本

- **元数据开销：** 如果平台会把可用 Skill 的描述放入模型上下文，Skill 数量增加就会带来额外开销。
- **正文开销：** Skill 被加载后，正文同样占用上下文；写得越臃肿，越容易挤压当前任务空间。
- **读取延迟：** 按需读取参考资料可能增加工具调用轮次和执行延迟。

### 5.2 可靠性成本

- **漏触发：** 用户表达了相关需求，但模型没有选择对应 Skill。
- **误触发：** 不相关任务也加载了 Skill。
- **遵循不完整：** Skill 已经加载，不代表模型一定严格执行全部步骤。
- **能力冲突：** 多个 Skill 的适用范围重叠，描述和规则可能互相竞争。
- **模型差异：** 同一套指令在不同模型、不同上下文长度和不同运行环境下，效果可能不同。

### 5.3 工程维护成本

- 流程和 API 变化后，需要同步更新 Skill；
- 参考资料和脚本可能逐渐过期；
- 问题定位需要区分描述、正文、引用资源、脚本和模型执行等不同层次；
- 没有评测集时，很难判断一次修改究竟带来了提升还是回归。

### 5.4 安全成本

Skill 中的脚本可能执行文件读写、网络访问或其他操作。第三方 Skill 也可能包含不可信指令、外部资源引用和危险代码。

因此，Skill 不能绕过常规软件供应链治理：

- 安装前检查来源和代码；
- 对脚本执行范围进行审计；
- 不在 Skill 中硬编码密钥和凭据；
- 对敏感操作使用最小权限；
- 在隔离、可控的运行环境中执行脚本；
- 对外部输入和脚本输出进行校验。

## 6. 如何编写一个可维护的 Skill

这里不建议先写一份很长的说明文档。更有效的方式是先找到 Agent 的实际问题，再针对问题补充最小必要规则。

### 6.1 先评测，再编写

推荐按下面的顺序做：

1. **建立 baseline：** 不加载 Skill，让 Agent 执行几个代表性任务。
2. **记录失败点：** 记录具体漏了哪一步、误用了什么工具、输出哪里不符合要求。
3. **构造评测样例：** 把失败案例转成可重复执行的测试输入和预期行为。
4. **编写最小 Skill：** 只补足已经暴露出的缺口，不提前堆砌大量假设规则。
5. **对比验证：** 比较有 Skill 和无 Skill 时的成功率、工具调用、耗时和人工纠正次数。
6. **持续迭代：** 将新的失败案例加入评测集，避免修复一个场景却破坏另一个场景。

这就是 Evaluation-Driven Development（评测驱动开发）的思路：**不是凭感觉把 Prompt 越写越长，而是让真实失败案例决定 Skill 应该包含什么。**

### 6.2 description：它是路由信息，不是宣传文案

在采用描述驱动 Skill 选择的平台中，description 会影响模型是否发现并选择某项能力。它至少要说清楚：

- **What：** 这个 Skill 能完成什么；
- **When：** 什么情况下应该使用；
- **Keywords：** 用户可能使用的文件类型、动作和场景词；
- **Boundary：** 哪些相邻任务不属于它的职责。

例如：

```yaml
# 不够明确：不知道处理什么，也不知道何时使用
description: Helps with documents.

# 只说能力，没有触发场景
description: Generates commit messages from git diffs.

# 更明确：能力 + 使用场景
description: Generate commit messages by analyzing git diffs.
  Use when the user asks to write a commit message or review staged changes.
```

description 的措辞风格应与目标平台的约定保持一致。第三人称通常更容易写清楚能力主体，但不要把某一种写法误当成所有平台的硬性规范。

**关键点：触发条件不能只写在正文里。** 如果平台需要先根据元数据选择 Skill，那么模型还没读取正文，自然也无法依赖正文中的触发说明来决定是否加载。

### 6.3 正文只保留模型真正需要的内容

不要在 Skill 中重新解释模型已经掌握的常识。重点写：

- 业务或项目特有的知识；
- 必须遵守的流程和边界；
- 默认方案与例外条件；
- 容易出错的细节；
- 输出格式和验收标准。

指令的具体程度应与任务风险匹配：

| 任务特征 | 指令方式 | 例子 |
|---|---|---|
| 高自由度、低风险 | 给原则和检查方向 | 普通代码可读性建议 |
| 有推荐模式、允许变通 | 给默认方案、模板和例外条件 | API 文档生成 |
| 顺序敏感、失败代价高 | 给明确步骤、命令和校验条件 | 数据迁移、批量修改 |

窄桥需要护栏，开阔地只需要方向。不要用一套固定的指令密度处理所有任务。

### 6.4 主流程做入口，低频细节拆到 references

当正文开始不断增长时，不要继续往主文件里堆细节。可以按任务场景拆分参考资料，并在主流程中说明何时读取：

```markdown
# Data Analysis

## Workflow
1. 确认数据范围和统计口径。
2. 检查缺失值、重复值和异常值。
3. 根据分析目标选择指标。
4. 生成结果并执行校验。

## References
- 财务指标定义：见 [references/finance.md](references/finance.md)
- 产品指标定义：见 [references/product.md](references/product.md)
- 数据质量规则：见 [references/data-quality.md](references/data-quality.md)
```

设计时注意：

- 主文件保留目标、核心流程和导航；
- 参考文件按任务需要读取；
- 尽量避免 A 引用 B、B 再引用 C 的多层跳转；
- 长参考文件在顶部提供目录；
- 不要把拆分本身当成目标，文件过碎也会增加检索和理解成本。

具体文件大小和行数没有适用于所有模型、平台和任务的统一阈值。应通过实际评测观察读取完整性和上下文成本，而不是机械追求某个数字。

### 6.5 确定性逻辑交给脚本，判断和编排交给模型

适合脚本处理的事情：

- 文件解析和格式转换；
- 数据校验和计算；
- 批量处理；
- 结构化结果生成；
- 可以明确输入、输出和失败条件的重复操作。

适合模型处理的事情：

- 理解用户意图；
- 在多个流程之间做选择；
- 解释非结构化信息；
- 根据上下文组织分析和结果。

例如，要求模型每次临时生成一段代码解析同一种 CSV，结果可能受生成代码、边界处理和依赖环境影响。若解析规则已经稳定，应该考虑把它实现为经过测试的脚本，而不是每次让模型重新实现。

脚本也需要工程质量：

- 显式声明依赖和运行方式；
- 处理异常并返回可行动的错误信息；
- 避免无来源的魔法常量；
- 校验输入、输出和文件路径；
- 对删除、覆盖、迁移等高风险操作采用“计划 → 校验 → 执行”；
- 在目标运行环境中测试，而不是只在本机验证。

还要明确脚本是“执行”还是“供模型阅读参考”，不要让模型自行猜测。

### 6.6 多步骤任务用清单和反馈闭环

对于步骤较多的任务，可以在 Skill 中给出明确清单：

```markdown
## Release Workflow

- [ ] 检查变更范围
- [ ] 执行静态检查
- [ ] 运行相关测试
- [ ] 检查配置和迁移脚本
- [ ] 生成发布说明
- [ ] 校验最终产物

如果任一步骤失败：
1. 停止后续发布操作；
2. 记录失败原因；
3. 修复后重新执行失败步骤；
4. 校验通过后再继续。
```

清单的价值不是让文档看起来更完整，而是把执行状态和关键检查点显式化。对于有副作用的操作，必须有明确的失败停止条件。

## 7. 典型踩坑：从现象定位到解决

下面这些是文件式 Skill 开发中值得重点测试的典型问题。它们是工程排查模式，不应直接当作个人项目经历；如果用于项目复盘或面试，需要替换成自己真实观察到的现象和数据。

### 坑 1：Skill 装了，但模型就是不触发

- **现象：** 用户提出相关任务，模型仍然按自己的方式执行，没有使用预期 Skill。
- **可能原因：** description 太宽泛、缺少用户真实表达中的关键词，或触发条件只写在正文里。
- **排查：** 收集一组真实用户表达，检查模型是否能识别适用场景；同时加入不应该触发的负样本。
- **解决：** 重写 description，明确能力、触发场景和排除边界。
- **沉淀：** description 是能力发现和路由的重要输入，必须通过样例验证，不能只看文字是否通顺。

### 坑 2：不相关任务也触发，多个 Skill 相互抢占

- **现象：** 用户问一个普通问题，却加载了某个专用 Skill；或者两个职责相近的 Skill 被混淆。
- **可能原因：** description 范围过大，多个 Skill 的职责边界重叠。
- **排查：** 构造“不应触发”样例，检查误触发；梳理各 Skill 的输入、输出和职责范围。
- **解决：** 收窄描述，补充排除条件；必要时合并高度重叠的 Skill。
- **沉淀：** 触发评测必须同时有正样本和负样本。只优化召回率，容易把描述越写越宽。

### 坑 3：SKILL.md 越写越长，模型开始漏步骤

- **现象：** 规则不断增加，关键步骤被遗漏，正文也挤占了当前任务上下文。
- **可能原因：** 把背景知识、低频例外和通用常识全部写进主文件。
- **排查：** 对正文做删减实验，移除某段后重新运行评测，观察结果是否变化。
- **解决：** 主文件保留核心流程和导航；低频细节拆到参考文件；删除模型本来就知道的解释。
- **沉淀：** 每一段指令都应该有明确收益。没有带来可验证改善的内容，不一定值得占用上下文。

### 坑 4：参考文件拆得太碎，模型没有读到关键内容

- **现象：** 主文件指向一个参考文件，参考文件又指向其他文件，最终模型只读取了部分内容。
- **可能原因：** 引用链条过长、文件缺少导航，或读取策略没有覆盖关键章节。
- **排查：** 检查实际读取路径和最终上下文，而不是只检查文件是否存在。
- **解决：** 尽量让主文件直接链接关键参考资料；长文件提供目录；将关键约束放回主流程。
- **沉淀：** 文件拆分的目标是按需加载，不是制造多层跳转。

### 坑 5：该用脚本的地方，却让模型每次现场写代码

- **现象：** 同样的解析、校验或格式转换任务，每次生成不同实现，偶尔出现边界错误。
- **可能原因：** 把确定性操作描述成文字要求，却没有固定实现。
- **排查：** 统计重复任务中的代码差异、失败类型和人工修正成本。
- **解决：** 将稳定逻辑提炼成脚本，定义输入输出、错误处理和测试样例。
- **沉淀：** 模型适合判断和编排；规则明确、可重复验证的逻辑应优先交给代码。

### 坑 6：本地能跑，目标环境却失败

- **现象：** 脚本在开发机正常，换到 Agent 的执行环境后出现缺包、路径错误或网络不可用。
- **可能原因：** 把本地依赖、网络权限和文件系统行为当成了平台默认能力。
- **排查：** 明确目标环境的运行时、依赖、网络和文件权限。
- **解决：** 显式声明依赖，在目标环境测试；对不支持的能力设计降级路径。
- **沉淀：** Skill 文件可移植，不代表它依赖的执行环境也可移植。

### 坑 7：没有评测，改完感觉更好了，实际却发生回归

- **现象：** 某个案例变好了，另一个场景却开始漏步骤或误触发。
- **可能原因：** 只用单个成功案例判断质量，没有固定 baseline 和回归样例。
- **排查：** 对比修改前后的触发结果、任务输出和失败案例。
- **解决：** 建立触发测试、任务测试和回归测试；每次改动都跑一遍。
- **沉淀：** Skill 的改动也应该像代码改动一样有测试证据。

### 坑 8：把第三方 Skill 当成普通 Prompt 直接安装

- **现象：** Skill 中包含来源不明的脚本、外部下载地址，或要求访问敏感文件和凭据的指令。
- **可能原因：** 只检查了功能描述，没有审计它实际会执行什么。
- **排查：** 检查脚本、依赖、网络请求、文件访问和凭据使用。
- **解决：** 只使用可信来源；安装前审计；执行时使用最小权限和隔离环境。
- **沉淀：** Skill 可能同时包含指令和可执行代码，应按软件供应链资产治理，而不是只当作文档。

## 8. 如何评测 Skill 是否真的有价值

至少要区分三个问题：能不能正确触发、触发后能不能完成任务、引入它是否值得。

| 评测类型 | 核心问题 | 评测方式 |
|---|---|---|
| 触发评测 | 该用时能否触发，不该用时是否保持不触发 | 正样本 + 负样本 |
| 任务评测 | 加载后是否按预期完成任务 | 代表性任务 + 明确验收标准 |
| 回归评测 | 修改后是否破坏原有能力 | 与 baseline 和上一版本对比 |

建议记录的指标：

- 触发召回率；
- 误触发率；
- 任务成功率；
- 关键步骤完成率；
- 平均 Token 消耗；
- 工具调用轮次和端到端耗时；
- 人工纠正次数；
- 不同模型和运行环境下的表现差异。

一个简单的评测样例可以这样组织：

```json
{
  "skill": "pdf-processing",
  "trigger_tests": {
    "should_trigger": [
      "提取这个 PDF 中的所有表格",
      "把这几个 PDF 文件合并"
    ],
    "should_not_trigger": [
      "总结下面这段普通文本",
      "帮我分析这个 Excel 文件"
    ]
  },
  "task_tests": [
    {
      "input": "从 sample.pdf 提取表格并保存为 CSV",
      "expected": [
        "使用约定的提取流程",
        "生成 CSV 文件",
        "校验输出文件存在且行列结构符合预期"
      ]
    }
  ]
}
```

不要把“模型说自己使用了 Skill”当成任务成功的充分证据。更重要的是检查可观察行为和最终结果：关键步骤是否执行、工具参数是否正确、产物是否通过校验。

### 8.1 一个轻量迭代闭环

```text
收集失败案例
    ↓
定位问题层级
(description / 指令 / references / scripts / runtime)
    ↓
只修改最可能的原因
    ↓
运行触发、任务和回归评测
    ↓
比较 baseline 与新版本
    ↓
保留改进，继续观察
```

| 症状 | 优先检查 |
|---|---|
| 不触发或误触发 | description、职责边界、正负样本 |
| 触发了但漏步骤 | 主流程、指令优先级、清单和验收标准 |
| 参考信息缺失 | 引用路径、读取策略、文件导航 |
| 输出不稳定 | 默认方案、模板、脚本和输入约束 |
| 目标环境执行失败 | 依赖、权限、网络和运行时 |
| 修改后其他任务变差 | 回归样例和 Skill 之间的职责冲突 |

## 9. 经验总结

1. **先解决重复出现的问题，再抽象 Skill。** 不要为了模块化而模块化。
2. **description 是路由信息。** 写清楚做什么、何时使用和不适用的边界，并通过正负样本验证。
3. **渐进式披露是上下文管理策略。** 主流程优先，细节按需读取，但具体加载行为取决于平台。
4. **模型负责判断和编排，脚本负责确定性操作。** 不要让模型反复生成本来可以固定实现的逻辑。
5. **指令数量不等于能力质量。** 删除没有带来可验证收益的规则。
6. **自由度要匹配风险。** 开放任务给原则，高风险操作给明确步骤和校验。
7. **Skill 是需要持续维护的软件资产。** 版本管理、Code Review、测试和安全审计都不能省。
8. **以真实运行结果迭代。** 不只看文档写得是否完整，更要看 Agent 实际如何触发、读取和执行。
